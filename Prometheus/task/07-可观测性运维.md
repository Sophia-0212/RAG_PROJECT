# 07. 可观测性 / 运维

> 模拟 iCafe 卡片，用于教学。所有客户信息、对话内容、人名均为虚构。

可观测性类需求的核心价值：这类卡片解决的不是"当前这一个问题"，而是"下一次类似问题能不能被更快发现"，是一种面向未来的投资。团队里"没有监控就等于蒙眼开车"这句话背后的具体含义，往往体现在下面这些真实案例里——出问题时才发现"我们连这个数据都没有"，比问题本身更让人沮丧。

## CRM-3260　[Story-P1] 新增"检索到 0 条结果"场景的告警和自动归因

**发现渠道**：客服投诉倒查（这次是先有客户反馈，团队才发现监控存在缺口——这本身就是问题所在，暴露了"应该被监控发现但没有被监控发现"的短板）。

**发现过程**：
1. 某业务线的客服团队负责人在周会上反馈，最近几天该业务线相关问题的助手回答质量明显变差，很多问题直接回答"暂无相关信息，建议联系人工"。
2. 数据分析师周涵接手排查，查看该业务线相关问题的检索日志，发现确实有大量请求的检索结果是空列表（0 条召回），且这个现象已经持续了 3 天。
3. 周涵进一步查为什么这个问题持续 3 天都没有被主动发现，答案是：现有监控大盘只统计"平均 Recall"和"平均响应时间"这类聚合指标，而"零召回"是个相对少数、被平均值稀释掉的现象，聚合指标层面完全看不出异常，必须像这次一样按业务线拆开逐个看才能发现。
4. 最终定位到根因是该业务线 3 天前做过一次索引更新，更新脚本执行时因为一个字段名变更导致该业务线的索引实际写入失败，但写入失败的错误没有被正确捕获上报，系统"看起来"更新成功了。

**结论/方案**：两方面补救：一是给"检索到 0 条结果"这个事件单独建立监控指标和告警阈值（比如某业务线某小时内零召回率超过某个百分比就告警），不再只依赖被平均值稀释的聚合指标；二是给索引更新脚本补充写入结果的强校验，写入失败必须有明确的错误上报和告警，不能"看起来成功"。

## CRM-3261　[Task-P2] 补充 LangGraph 工作流各节点的耗时打点，定位 P95 长尾

**发现渠道**：性能优化立项时发现的"监控盲区"（在做别的性能分析工作时发现自己缺少必要的数据支撑）。

**背景**：性能工程师孙睿在分析 P95 长尾请求（响应时间明显高于大多数请求的那一小部分）时，想知道这些慢请求究竟慢在哪个环节——是检索慢、重排序慢、还是模型生成慢，但发现当前监控体系只有"端到端总耗时"这一个指标。

**分析受阻过程**：
1. 孙睿尝试从现有日志里拆解慢请求的耗时构成，发现日志里只记录了请求开始和结束的时间戳，中间 LangGraph 工作流内部各个节点（检索节点、重排序节点、生成节点等）各自执行了多久，完全没有记录。
2. 孙睿只能靠"猜"和"抽样手动加日志复现"的方式去分析个别慢请求，效率很低，且无法批量统计"到底是哪个环节的耗时分布导致了长尾"，比如可能是 95% 的请求重排序都很快，但检索节点偶尔会因为 Milvus 抖动变得很慢，这种规律性的东西只能通过大量数据统计才能发现，靠人工抽查几个 case 是看不出规律的。

**结论/方案**：需要在 LangGraph 工作流的每个节点前后补充耗时打点，上报到监控系统，之后才能对长尾请求做"分环节耗时分布"的统计分析，把"猜测"变成"数据驱动的定位"。这是一个基础设施补齐类的任务，本身不直接解决某个具体问题，但是解决未来一系列问题的前提条件。

## CRM-3262　[Bug-P2] Token 消耗监控大盘和实际账单存在 15% 偏差

**发现渠道**：财务对账例行流程（业务外部门的常规工作触发的技术排查，跨部门协作发现问题的典型例子）。

**发现过程**：
1. 财务同学在做月度供应商账单核对时，发现模型供应商开具的账单 Token 用量，比技术团队监控大盘统计的用量高出约 15%，超出了财务认为可以接受的正常误差范围，找技术团队核实。
2. 后端工程师刘阳接手排查，先确认监控大盘的统计逻辑：目前是在每次请求"成功返回"时记录一次本次消耗的 Token 数量，累加到大盘。
3. 刘阳注意到系统存在请求失败自动重试的机制（比如模型服务瞬时抖动导致单次调用失败，系统会自动重试一次），于是检查重试逻辑里的 Token 统计情况，发现问题：重试后最终成功的请求，监控大盘只记录了"最后一次成功调用"消耗的 Token，而前面失败的那一次调用尽管没有返回结果，但依然实际消耗了供应商侧计费的 Token（模型侧已经做了计算，只是网络层面响应没有正常送达），这部分"失败但已计费"的 Token 完全没有被大盘统计进去。

**根因**：Token 消耗监控的统计口径是"以业务上是否成功为统计触发条件"，但供应商计费的口径是"以是否发起了计算为计费依据"，两个口径本质不一致，重试场景下必然会造成统计缺口，且重试发生的频率和账单周期内的偏差幅度直接相关。

**解决方案**：修改监控统计逻辑，改为在每一次实际发起的模型调用（无论成功失败）后都记录一次 Token 消耗（如果供应商在失败响应里也返回了消耗信息），或者至少对失败重试场景补充一个估算值兜底统计，让监控口径和真实计费口径对齐。
