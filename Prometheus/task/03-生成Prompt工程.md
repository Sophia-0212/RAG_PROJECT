# 03. 生成 / Prompt 工程

> 模拟 iCafe 卡片，用于教学。所有客户信息、对话内容、人名均为虚构。

生成类问题的排查特点：检索环节可能是对的（召回了正确文档），但模型"读了对的材料却给出错的结论"，这类问题往往需要**先排除是不是检索问题**，再往 Prompt 和生成策略上查，容易被误判为"检索又出问题了"，实际上是生成侧的锅。

## CRM-3220　[Bug-P0] 模型编造了不存在的客户折扣政策

**发现渠道**：Claim Groundedness 自动化评测抽检触发人工复核（评测体系主动发现，而非客户直接投诉——这类问题客户往往不会意识到自己被"编造的答案"误导了，直到后续走流程时才会暴露，所以更依赖评测体系主动兜底）。

**发现过程**：
1. 评测负责人赵蕾团队每天会对线上一批抽样问答做自动化 Claim Groundedness 打分（检测答案里的每句话是否能在检索到的文档里找到依据）。当天的自动化报表里有一条记录的 Groundedness 分数异常低（0.12），触发了人工复核队列。
2. 人工复核的评测同学"孙睿"打开这条记录，看到用户问题是"XX 客户能否享受连续包年 8 折优惠"，模型回答里明确给出了"该客户符合连续包年满 12 个月即享 8 折"的具体规则，语气非常肯定。
3. 孙睿去核对本次检索到的所有候选文档，发现召回的三篇文档里根本没有任何一篇提到"连续包年 8 折"这个具体规则——检索环节召回的是"套餐续费通用流程"等相关但不包含这个具体折扣数字的文档。

**排查人**：算法工程师陈昊接手复核结果，进一步排查生成侧原因。

**排查过程**：
1. 陈昊确认了检索环节本身没有问题（检索到的文档确实不包含这个规则，说明模型是在"没有依据"的情况下给出了具体数字），排除了检索侧的锅。
2. 陈昊复现该 query，查看当时的完整 Prompt，发现 Prompt 里对模型的指令是"结合以下参考资料回答用户问题"，但没有明确的"如果参考资料中未提及具体规则，必须明确告知用户无法确认，不要猜测或编造"这类强约束语句。
3. 陈昊做了对照实验：给同一个 query 换一个更强约束的 Prompt（加入"仅可依据参考资料回答，资料未提及的内容不可编造，须回复'当前资料未覆盖该问题，建议联系XX'"），模型正确地回复了"当前资料未能确认该具体折扣，建议核实"。

**根因**：Prompt 中缺少针对"检索依据不足时应该拒答而非编造"的强约束指令，模型在信息不足时倾向于用训练时学到的通用模式"编"出一个听起来合理的具体数字。

**解决方案**：为涉及折扣、价格、具体数字类的敏感问题，Prompt 模板统一加入强约束的拒答指令；同时评估是否需要针对这类高风险问题类型（涉及具体金额/规则数字）设置更严格的 Groundedness 阈值门槛，低于阈值直接拦截不返回给用户，走人工兜底。

## CRM-3221　[Story-P1] 审批类问答需要区分"我能做什么"和"我该走什么流程"两种意图

**发现渠道**：客服组每周质量会议上的集中反馈（多个客服反复提到同一类问题，被质检同学汇总后升级为需求）。

**业务方反馈原话**：
质检同学韩梅在周会上汇总："这周有 4 位客服都提到，客户问'我能不能给这个客户改归属'，助手只回答'可以，归属变更权限允许跨区域调整'，但客户接着问'那我具体怎么操作'，助手又要重新问一遍才给流程，用户体感是每次都要问两遍才能问完一件事。"

**排查人**：算法工程师陈昊 + 产品经理林晓共同分析（这是产品体验问题，需要产品和算法协同定义，不是纯技术 bug）。

**分析过程**：
1. 陈昊抽取了 50 条类似的用户 query，发现这些问题的共同特征是：用户的表述里其实同时隐含了"是否允许"（权限判断）和"如何操作"（流程步骤）两层意图，但原始 Prompt 模板是"根据检索内容直接回答用户问题"，没有对这类复合意图做拆解，模型往往只挑其中一层意图回答（通常是先命中"是否允许"这层，因为政策类文档里"是否允许"的描述往往在段落最前面，检索排序上更靠前）。
2. 林晓补充了用户体验角度的分析：这类审批场景下，用户真正想知道的几乎总是"两层都要"，因为"能做"和"怎么做"对完成任务同样重要，缺一不可,这和纯知识问答场景（用户往往只想知道一个事实）不一样。

**结论/方案**：针对识别为"审批/操作类"意图的问题，调整 Prompt 模板，明确要求模型在回答中同时覆盖"权限判断结论"和"具体操作步骤/所需走的审批流程"两部分内容，即使检索到的文档里两部分内容来自不同的 chunk，也要求生成时合并呈现。

## CRM-3222　[Task-P2] 优化 Token 消耗，评估直接答案路由的覆盖率

**发现渠道**：成本分析报告（财务和技术团队联合复盘时发现的优化机会，非故障）。

**背景**：技术负责人在月度成本复盘会上提出，当前平均 Token/请求为 3,760，希望评估是否有可以进一步压缩的空间，而不是所有问题都走"检索+重排序+完整生成"的重路径。

**分析过程**：
1. 数据分析师周涵抽取近一周的问题日志，按"问题复杂度"人工标注分类，发现约 22% 的问题属于"事实型简单问题"（如"XX功能入口在哪个菜单""XX状态对应的英文缩写是什么"），这类问题理论上不需要完整的检索+重排序+多轮生成流程，用一次简单检索+直接生成就足够。
2. 周涵进一步核对现有的"直接答案路由"（一种更轻量的快速通道）的实际命中率，发现只有 9% 的问题被正确路由到了这个快速通道，远低于理论上 22% 的简单问题占比，说明快速通道的判断规则过于保守，很多本该走快速通道的问题被误判为复杂问题走了重路径。
3. 抽样看了几个被误判的 case，发现快速路由的判断逻辑主要依赖问题长度和关键词规则，对一些"看起来复杂但实际很简单"的问题（比如包含"如何"这类词但实际答案是一个固定入口位置）容易误判为复杂问题。

**结论/方案**：评估优化直接答案路由的判断规则（引入轻量分类模型替代纯规则判断），目标是把命中率从 9% 提升到接近理论上限的 20% 左右，预计可以在不影响这批问题回答质量的前提下降低整体平均 Token 消耗。

## CRM-3223　[Story-P2] 多轮对话中用户澄清后，答案未能结合上一轮上下文

**发现渠道**：产品经理林晓在自己试用产品时发现（内部"吃自己的狗粮"式测试，很常见的发现渠道）。

**发现过程**：
林晓在做多轮对话体验自查时，模拟了一次真实场景对话：
- 用户："续费规则是什么？"
- 助手："请问您想了解的是企业版还是标准版的续费规则？"
- 用户："企业版"
- 助手：（重新检索"企业版"相关内容，但给出的答案是企业版的"功能介绍"，完全没有提到"续费"）

林晓判断这是个明显的体验问题，报给了算法工程师陈昊。

**排查人**：陈昊。

**排查过程**：
1. 陈昊复现对话流程，查看第二轮请求实际发给检索模块的 query，发现系统把第二轮用户输入"企业版"单独作为检索 query 发出，完全没有拼接第一轮的"续费规则"这个原始意图。
2. 陈昊查看多轮对话的上下文管理逻辑，发现当前策略是"每轮检索使用用户最新一句输入"，这种策略在用户输入信息完整时没问题，但当用户是在回答助手的澄清问题（比如只回答"企业版"这一个词）时，最新一句输入本身信息量严重不足，必须结合上一轮的原始意图才能构成完整检索意图。

**根因**：多轮对话的检索 query 构建策略没有区分"用户主动提问"和"用户回答澄清问题"这两种不同性质的输入，对后一种情况缺少和历史轮次意图的拼接逻辑。

**解决方案**：识别当前轮是否是对助手澄清问题的回答（可以通过判断上一轮助手是否发出过澄清问句），如果是，则将当前轮输入与被澄清的原始意图拼接后再作为检索 query，而不是直接使用最新一句话。
