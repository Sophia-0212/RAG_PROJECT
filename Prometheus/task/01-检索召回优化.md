# 01. 检索 / 召回优化

> 模拟 iCafe 卡片，用于教学。所有客户信息、对话内容、人名均为虚构。

检索召回类问题的共性排查链路：**客服/业务方反馈"答案不对"（症状）→ 数据分析师或算法工程师复现 query → 打印召回中间结果（BM25 分数、向量分数、RRF 融合分数、重排序分数）→ 定位是哪一路召回或哪一环融合出了问题**。这条链路本身比结论更重要——请重点看"排查过程"部分，那是真实工作中占时间最多的环节。

## CRM-3210　[Bug-P0] 客户 A 询问续费流程，召回的 Top1 是完全不相关的退款政策

**发现渠道**：客服工单系统。一线客服"王婷"在系统里对同一个问题连续两次给出了错误答案，被客户投诉后升级为工单。

**客户/业务方反馈原话**：
客户在企业微信客服群里问："我们公司的企业版马上到期了，续费流程是怎样的？"客服坐席把问题转给内部 RAG 助手，助手返回的答案第一句是"退款需在购买后 7 个自然日内申请，且产品需处于未激活状态"。客服判断答案完全跑偏，无法向客户解释，把这条对话截图报给了值班的算法工程师"陈昊"。

**排查人**：算法工程师陈昊（负责检索链路的兜底 owner）。

**排查过程**：
1. 陈昊先在评测后台用相同 query "企业版续费流程"复现问题，确认线上确实稳定复现，不是偶发。
2. 打开检索调试面板（内部工具，能看到 Milvus 稠密召回、BM25 稀疏召回、RRF 融合后三份 Top10 列表和各自分数），发现：
   - Milvus 稠密召回的 Top1 是"企业版续费与升级指引"，语义相关，分数正常；
   - BM25 稀疏召回的 Top1 却是"7日无理由退款政策"，BM25 分数远高于其他候选。
3. 陈昊怀疑是分词或字面匹配问题，把两个文档的标题和 query 一起丢进分词工具查看：query 分出"企业版/续费/流程"，退款政策文档标题分出"企业版/购买/退款"——共享了高权重词"企业版"，而 BM25 是纯词频统计模型，不理解"续费"和"退款"语义相反，只看到两篇文档都密集出现"企业版"这个词，且退款政策文档里"企业版"出现频次更高（因为文档反复提到"企业版用户需在xx天内..."），导致 BM25 分数虚高。
4. 进一步查看 RRF 融合权重配置，发现 BM25 和稠密召回的融合权重是 1:1，退款文档凭着 BM25 高分把语义上完全不相关的内容顶到了 RRF 融合后的 Top1，盖过了稠密召回本来给出的正确答案。

**根因**：BM25 稀疏召回对"续费"和"退款"两个语义相反但共现高权重词"企业版"的文档给出了虚高分数，且 RRF 融合权重没有对这种"字面像、语义不像"的情况做抑制。

**解决方案**：短期给 BM25 召回结果加一层否定词过滤（"退款"命中时若 query 不含退款相关意图词则降权）；中期评估在 RRF 融合前引入一次轻量语义相似度阈值过滤，把语义相似度过低的候选提前剔除，不让它们进入融合排名。

## CRM-3211　[Story-P1] 针对客户成功场景，评估是否需要引入 query 改写/多路召回

**发现渠道**：季度用户访谈 + 有帮助率数据分析。产品经理"林晓"每季度会抽访 10 名客户成功经理，同时数据分析师会跑一次"有帮助率"分维度报表。

**业务方反馈原话**：
访谈中三位客户成功经理独立提到同一个抱怨："我经常就打几个字问，比如'这个客户能不能改标签'，它有时候懂我在问权限，有时候又开始讲标签体系介绍，很不稳定。"林晓把这个反馈同步给了数据分析师"周涵"。

**排查人**：数据分析师周涵 + 算法工程师协同评估（这是 Story 不是 Bug，走的是分析评估流程，不是应急排查）。

**排查过程**：
1. 周涵从日志里按"客户成功经理"角色过滤出近 30 天的问题日志，人工抽样 200 条，发现平均 query 长度只有 6.3 个字，远低于全站平均 14.1 个字。
2. 对比这 200 条里"有帮助"和"无帮助"两组，发现"无帮助"组里有 62% 的 query 是模糊指代型（如"这个客户""刚才那个操作"），且原始 query 本身缺乏明确意图词，导致向量召回把语义相近但意图不同的多个文档拉到了相近的分数区间，排序不稳定。
3. 周涵和算法同学做了一次简单实验：把这 200 条模糊 query 手动改写成完整问句（比如把"这个客户能不能改标签"改写成"销售经理是否有权限修改客户标签属性"）后重新跑召回，Recall@10 从 58% 提升到 79%。

**根因**：客户成功场景下用户输入习惯性简短、指代不清，原始 query 的语义信息量不足以支撑向量召回稳定区分意图。

**结论/方案**：评估引入 query 改写模块（在检索前用小模型把简短 query 结合对话历史改写为完整问句），或者引入 HyDE（先让模型生成一个假设性答案再用假设答案去检索）。需要先在离线评测集上 A/B 两种方案再决定。

## CRM-3212　[Task-P2] CrossEncoder 重排序模型在长尾 SOP 场景上的精度评估

**发现渠道**：内部评测体系的分场景报表（不是客户直接反馈，是评测体系主动发现的"暗雷"）。

**背景**：评测负责人"赵蕾"按季度会把评测集按"高频场景"和"长尾场景"（周问答量低于 5 次的场景）拆开看指标，而不是只看整体平均分，这是团队自己养成的习惯——整体平均分很容易被高频场景的好表现"平"掉长尾场景的差表现。

**排查/分析过程**：
1. 赵蕾按场景标签把评测集拆分后发现，长尾场景（如"批量转移客户后如何回滚"这类低频操作类问题）的 Recall@10 只有 61%，比整体的 85.1% 低了 24 个百分点，但因为长尾场景占比小，整体均值没有暴露出这个问题。
2. 抽查这些长尾 case 发现，CrossEncoder 重排序模型给正确答案打的相关性分数普遍偏低（0.3~0.4 区间），而给一些字面相似但操作不同的文档打了 0.5~0.6，说明重排序模型本身对这类低频、操作步骤细节差异大的文本区分能力不足。
3. 推测原因：CrossEncoder 微调时使用的训练数据主要来自高频问答日志的人工标注，长尾操作类的正负样本数量很少，模型对这类模式学习不充分。

**根因**：重排序模型的训练数据分布和长尾场景的真实分布不匹配，属于训练数据覆盖不足，不是线上 bug。

**结论/方案**：需要针对长尾操作类问题补充标注数据（至少覆盖 Top 50 个低频高价值操作场景），重新微调或评估是否对这类场景走规则兜底而非纯模型排序。

## CRM-3213　[Story-P2] Recall@10 从 85.1% 进一步提升，评估分层召回（按业务线预过滤）

**发现渠道**：架构评审会上算法负责人主动提出的优化方向（不是问题驱动，是主动的性能/质量提升立项）。

**背景**：客户档案量 3100 万，chunk 186 万，随着知识库持续增长，算法负责人"孙睿"在双周架构会上提出，当前召回是在全量 186 万 chunk 里做一次性检索，随着 chunk 量增长，噪声候选（来自不相关业务线的文档）也在同步增长，担心 Recall 会随知识库扩张而缓慢下降。

**分析过程**：
1. 孙睿让数据分析师统计了 Top10 召回结果里"业务线不匹配"（即召回的文档所属产品线和提问用户所属产品线不一致）的比例，发现约有 18% 的 Top10 候选属于不匹配业务线，这些候选大概率是纯粹的噪声，占用了排序位置。
2. 做了一次简单的分层实验：先按用户所属业务线粗过滤 chunk 池，再在过滤后的子集里做精排召回，同一批评测集上 Recall@10 从 85.1% 提升到 88.4%。

**结论/方案**：评估在生产环境引入"业务线预过滤 + 精排"的两级召回架构，需要补充评估预过滤规则的误判成本（比如用户档案里业务线标注不准确会导致该被召回的内容被误过滤掉）。

## CRM-3214　[Bug-P1] RRF 融合参数在高并发下出现召回结果不稳定

**发现渠道**：内部质量抽检 + 客服反馈交叉印证。质检同学"韩梅"在做人工抽检时发现同一个问题被不同客服问了两次，答案不一样。

**业务方反馈原话**：
韩梅在质检群里发消息："同一句话'客户分级规则是什么'，我上午问一次、下午又问一次，Top1 答案不一样，一次是分级规则文档，一次是分级调整流程文档，这正常吗？"

**排查人**：后端工程师"刘阳"（负责检索服务的稳定性）。

**排查过程**：
1. 刘阳先确认这两次请求打到的是同一个索引版本，排除了"知识库刚好在这期间更新"的可能。
2. 追踪链路日志发现，这两次请求分别是在低并发和高并发时段发出的。刘阳怀疑和并发有关，于是做压测复现：在低并发下连续请求 50 次同一 query，结果 100% 稳定；把并发拉到 12（即单 worker 并发上限）以上重复请求，结果开始出现约 15% 的不一致。
3. 深挖 RRF 融合逻辑代码，发现 Milvus 稠密召回和 BM25 稀疏召回是两个并行发出的异步请求，各自有独立的超时降级策略（超时后返回空列表而不是报错）。在高并发下，BM25 服务的响应有时会逼近超时阈值，一部分请求触发了降级（返回空的稀疏召回结果），另一部分因为响应快了几十毫秒没有触发降级，导致同一个 query 在不同请求里参与 RRF 融合的候选集不一样，融合结果自然不同。

**根因**：两路召回的超时降级策略阈值设置不一致（且都比较接近高并发下的真实响应时间），高并发下触发降级的概率不稳定，导致参与融合的候选集时有时无、结果不确定。

**解决方案**：统一两路召回的超时阈值并留出安全余量，同时给"触发降级"这个事件加监控埋点和告警，避免这类隐性不稳定性再次悄悄发生而无人知晓。
