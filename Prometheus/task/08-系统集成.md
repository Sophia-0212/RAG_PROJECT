# 08. 系统集成

> 模拟 iCafe 卡片，用于教学。所有客户信息、对话内容、人名均为虚构。

系统集成类问题的共性：RAG 系统本身可能完全没有 Bug，问题出在"和外部系统对接的那条边界线上"——这类问题最难排查的地方在于，两个系统各自看自己的日志都是"正常"的，只有把两边的数据拼起来对照才能发现问题，往往需要跨团队协作才能定位根因。

## CRM-3270　[Story-P1] ONECRM 客户档案变更后，RAG 侧的客户上下文未及时同步

**发现渠道**：客户成功经理的具体业务投诉（有明确的业务后果，不是抽象的技术问题）。

**业务方反馈原话**：
客户成功经理"陈静"反馈："我昨天刚把一个客户的等级从'标准'调整到了'核心'，今天早上问助手这个客户享受什么权益，它说的还是标准等级的权益，客户那边已经在问我核心权益的事了，这个时间差太尴尬。"

**排查人**：后端工程师刘阳。

**排查过程**：
1. 刘阳先确认 ONECRM 系统侧的客户等级数据确实已经是最新的"核心"等级，说明问题不在 ONECRM 那一侧。
2. 刘阳查看 RAG 侧客户上下文的更新机制，发现当前架构是"RAG 侧维护一份客户档案的本地缓存/索引副本，定时从 ONECRM 拉取增量更新，同步周期是每 24 小时一次"。
3. 陈静修改客户等级的时间点，刚好是在当天的同步任务执行完毕之后，所以这次变更要等到第二天的同步任务才能被拉取过来，中间自然存在最长接近 24 小时的数据延迟窗口，这次陈静的具体案例正好撞在了这个延迟窗口里。

**根因**：RAG 侧和 ONECRM 之间是定时批量拉取的同步机制，本质上是"最终一致性"而非"实时一致性"，对于客户等级这类变更频率不算高但一旦变更就需要尽快生效的字段，24 小时的同步延迟在业务上是不可接受的。

**结论/方案**：评估从"定时批量拉取"改为"事件驱动同步"（ONECRM 侧发生客户档案变更时主动推送事件通知，RAG 侧监听并实时更新对应客户的上下文），至少要对"客户等级"这类高敏感度字段优先做事件驱动改造，而不是所有字段都等 24 小时批量同步。

## CRM-3271　[Bug-P1] Dify 二次开发的工作流节点调用 RAG 接口时未传租户上下文

**发现渠道**：安全测试团队对新上线工作流节点的例行安全测试（不是等出问题，是新功能上线前的标准安全检查项）。

**发现过程**：
1. 业务团队用 Dify 平台二次开发了一个新的自动化工作流节点，节点内部会调用公司 RAG 服务的 API 来获取知识问答能力，用于工作流中某个自动判断步骤。
2. 安全测试工程师韩梅在这个新工作流节点正式上线前按流程做安全测试，其中一项是检查该节点发起的 RAG 调用是否正确携带了发起方的租户身份信息。
3. 韩梅用测试环境模拟调用，发现该工作流节点调用 RAG 接口时，请求参数里完全没有传递租户 ID 字段，进一步测试发现，RAG 服务端在缺少租户 ID 时的默认行为是"降级为不做租户过滤的全量检索"（这是接口早期设计时为了兼容一些内部调试场景留下的默认行为）。

**排查人**：后端工程师刘阳协助分析根因。

**排查过程**：
刘阳排查发现，Dify 平台的工作流节点开发是由业务团队自主完成的二次开发，业务团队的开发人员在参考 RAG 接口文档时，文档里把租户 ID 标注为"可选参数"，业务团队开发时没有意识到"可选"在这个场景下的实际含义是"不传就会导致检索范围失控"，而只是理解为"看起来不传也能正常返回结果，那就先不传"。

**根因**：接口契约把一个实际上安全攸关的必填参数错误地标注为"可选"，且服务端在参数缺失时选择了"静默降级为不安全的默认行为"而不是拒绝请求，这是接口设计层面的缺陷，被下游一个不知情的调用方无意中触发了。

**解决方案**：立即修改接口契约，把租户 ID 改为强制必填参数，服务端在缺少该参数时直接拒绝请求并返回明确错误，而不是静默降级；同时把这次问题同步给所有已知的下游调用方（包括 Dify 工作流、其他内部系统），要求排查是否存在类似的未传租户上下文的调用。

## CRM-3272　[Task-P2] IAM 权限变更后，审批执行接口的鉴权缓存未及时失效

**发现渠道**：安全审计（内部权限变更响应时效性的专项检查）。

**发现过程**：
1. 安全团队做了一次专项测试：模拟收回某个测试账号的审批执行权限后，立即用该账号尝试发起需要该权限的审批动作，观察系统能多快正确拒绝该请求。
2. 测试发现，权限被收回后的头几分钟内，该账号依然能够成功发起本该被拒绝的审批动作，直到大约 5 分钟后才开始被正确拒绝。

**排查人**：后端工程师刘阳。

**排查过程**：
刘阳查看审批执行接口的鉴权实现，发现为了减少每次请求都实时查询 IAM 系统带来的延迟开销，接口对用户权限结果做了本地缓存，缓存 TTL（存活时间）设置为 5 分钟。这个设计在"权限只会变得更宽松"或者"权限变更不敏感"的场景下问题不大，但对于"权限被收回"这种需要尽快生效的安全敏感场景，5 分钟的缓存窗口意味着有权限的人被收权后，仍有最多 5 分钟的窗口期可以继续执行本不该被允许的操作。

**根因**：鉴权缓存的 TTL 设置是从"减少 IAM 系统查询压力、降低接口延迟"这一性能角度出发做的权衡，没有充分考虑到"权限收回"场景下的安全时效性要求，两个诉求（性能和安全时效性）之间的权衡点选择偏向了性能一侧。

**结论/方案**：评估引入权限变更的主动失效机制（IAM 侧权限变更时主动推送失效通知，而不是被动等缓存过期），或者至少针对"审批执行"这类高敏感操作单独设置更短的缓存 TTL，用局部的性能损耗换取安全时效性的提升，不需要为了这一类高敏感接口牺牲全局的缓存策略。
