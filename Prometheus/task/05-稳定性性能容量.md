# 05. 稳定性 / 性能 / 容量

> 模拟 iCafe 卡片，用于教学。所有客户信息、对话内容、人名均为虚构。

稳定性类问题的共性：往往是**监控告警先响，值班工程师被叫醒去看，而不是等客户投诉**——这是成熟系统和 Demo 级系统的核心区别之一：真正的生产系统靠自己的监控发现问题，客户投诉是"监控失守"之后的最后一道防线，不应该是第一道。

## CRM-3240　[Bug-P0] 峰值时段 API Pod 连接池打满，PostgreSQL 报 "too many connections"

**发现渠道**：监控告警自动触发（PagerDuty/内部告警系统），值班工程师"刘阳"凌晨被叫起来处理。

**告警内容**：
监控大盘触发 P0 告警："PostgreSQL 活跃连接数持续超过预算上限（48），API 请求错误率从 0.3% 飙升至 18%。"同时客服组也开始陆续反馈"助手最近老是超时或者报错"，但这个反馈是在告警已经触发几分钟后才陆续出现的，说明监控确实跑在了客户感知前面。

**排查人**：刘阳（值班工程师，负责当晚 on-call）。

**排查过程**：
1. 刘阳先看监控大盘确认告警不是误报，PostgreSQL 连接数图表显示确实在短时间内从平时的 20 左右飙升到 48 并持续报错，说明连接池确实被打满。
2. 查看同一时间段的 QPS 曲线，发现同一时刻请求量出现了一个远超日常峰值（9 QPS）的尖峰，达到约 34 QPS，持续了将近 6 分钟。
3. 刘阳去查这个流量尖峰的来源，发现同一时间点，业务方刚好上线了一个新的营销活动，触发了一批"客户批量打标签"的工作流，这些工作流集中在活动开始的同一分钟内被大量触发，每个工作流内部都会调用一次 RAG 接口做规则校验，短时间内堆积成了流量尖峰。
4. 进一步查看连接池配置，确认当前"每 Pod 1-16"的连接池上限设计，是按日常 9 QPS 峰值场景估算的，没有为这种"工作流批量触发型"的短时尖峰预留额外余量。

**根因**：连接池容量规划只覆盖了日常人工提问的峰值场景，没有考虑到工作流批量触发可能产生的短时超预期尖峰流量，这类尖峰的量级和日常峰值不是同一个数量级。

**解决方案**：短期先给工作流触发的 RAG 调用加一层独立的限流队列，避免这类批量触发直接打满连接池；中期评估是否需要给连接池上限增加弹性伸缩能力，或者要求业务方的批量触发场景必须走异步队列而非同步直接调用。

## CRM-3241　[Task-P1] 审批恢复 Worker 在故障重放时占用了过多 CPU，影响 API Pod 同节点资源

**发现渠道**：故障复盘会议上发现的次生问题（不是独立发现的问题，是在排查另一次故障时顺带发现的关联问题）。

**背景**：某次上游模型服务短暂不可用导致一批审批请求失败进入重试队列，故障恢复后，恢复 Worker 按配置（每 Pod 恢复并发 2，恢复窗口 300 秒）开始集中重放这批失败请求。故障复盘会上，SRE 同学"孙睿"发现虽然核心故障已经处理完，但恢复期间 API 请求的 P95 延迟也出现了一次不该有的抬升。

**排查人**：SRE 孙睿。

**排查过程**：
1. 孙睿查看故障期间的节点级 CPU 监控（不是 Pod 级，是物理节点级别），发现在恢复 Worker 集中重放的那几分钟，同一个物理节点上的 CPU 使用率出现了明显抬升。
2. 孙睿核对了节点上的 Pod 分布，发现当前的调度策略没有对"API Pod"和"恢复 Worker"做节点级别的反亲和性配置（即两者可能被调度到同一台物理机上），这次故障期间刚好有一个 API Pod 和一个恢复 Worker 分到了同一节点。
3. 恢复 Worker 集中重放时会同时进行模型调用等 CPU/网络密集操作，虽然从"Pod 资源限额"层面看两者都没有超过各自申请的资源上限，但物理节点整体的 CPU 是共享资源，恢复 Worker 的突发负载挤占了同节点 API Pod 实际能用到的 CPU 时间片，导致该 API Pod 上的请求处理变慢，抬高了局部 P95。

**根因**：恢复 Worker 和 API Pod 在逻辑上各自独立部署（不共享应用层资源池），但在物理调度层面没有做节点级隔离，两者仍可能竞争同一台物理机的硬件资源。

**解决方案**：给恢复 Worker 和 API Pod 配置节点反亲和性规则，确保两者不会被调度到同一物理节点，从物理资源层面彻底隔离，避免"逻辑隔离但物理共享"这种隐性风险。

## CRM-3242　[Story-P2] 评估 Reranker 推理是否需要拆分为独立服务，避免阻塞事件循环

**发现渠道**：上线前压测（主动的性能验证流程，不是线上故障）。

**背景**：性能工程师"孙睿"在为新一轮容量评审做压测时，按计划测试系统在理论 36 并发槽位下的真实表现。

**压测过程**：
1. 孙睿逐步加压，发现当并发数超过 8 左右时，P95 延迟开始出现明显的非线性抬升，而不是预期中的平稳增长，怀疑某个环节存在阻塞。
2. 孙睿在压测时同步观察各环节耗时打点，发现"检索"和"模型生成"两个环节的耗时随并发增长比较平缓，但"重排序"这一步的耗时随并发增长呈现明显的排队效应——并发数从 4 到 8，重排序平均耗时几乎翻倍。
3. 孙睿去看重排序模块的实现方式，发现 CrossEncoder 重排序是在应用主进程的事件循环里直接同步调用模型推理（没有丢到独立线程池或独立服务），这是一个 CPU 密集型操作，会独占事件循环，导致同一时刻其他并发请求即使只是在等待 I/O（比如等 Milvus 返回），也会被这个正在跑重排序的请求"卡住"，无法及时被事件循环调度处理。

**根因**：重排序模型推理是 CPU 密集型阻塞操作，被直接放在了为 I/O 密集型场景设计的异步事件循环里同步执行，违背了异步框架"绝不能有阻塞事件循环的同步计算"这一基本假设，导致高并发下出现请求排队和相互阻塞。

**结论/方案**：评估两种方案：一是把重排序推理放入独立的线程池/进程池异步执行（`run_in_executor`），二是把重排序拆分为独立的推理微服务，通过网络调用而非进程内调用。需要评估两种方案的延迟和资源成本差异后决策。

## CRM-3243　[Bug-P1] 目标环境压测发现实际并发远低于理论 36 槽位

**发现渠道**：上线前的标准压测流程（容量规划卡片，团队规范要求任何新容量配置上线前必须过压测）。

**背景**：这是文档里提到的"3 Pod × 1 worker × 12 并发 = 36 槽位"配置定稿前的验证环节，性能工程师孙睿负责执行压测并出具报告。

**压测过程**：
1. 孙睿搭建目标环境的压测集群（与生产环境规格一致），逐步提高并发请求数，观察系统在什么并发水位下开始出现明显的延迟劣化或错误率上升。
2. 压测结果显示，系统在并发数达到约 22 左右时，P95 延迟已经开始明显偏离线性增长趋势，超过 22 之后错误率也开始出现小幅上升，远低于理论计算的 36 槽位。
3. 孙睿结合 CRM-3242 的排查结论（重排序阻塞事件循环）分析，认为理论槽位计算假设的是"每个 worker 能真正同时处理 12 个请求"，但实际上由于重排序环节的阻塞效应，同一 worker 在处理重排序密集的请求时，事实上没办法真正同时处理 12 个请求，实际可用并发被打了折扣。

**根因**：理论槽位计算（3×1×12=36）建立在"worker 的 12 个并发都能被充分利用"这一假设上，但该假设的前提是所有耗时环节都是异步非阻塞的，而实际存在的重排序阻塞问题（见 CRM-3242）导致这个假设不成立，实际可用并发明显低于理论值。

**解决方案**：本次压测报告作为决策依据，建议：一是先推进 CRM-3242 的重排序异步化改造以尽量逼近理论并发能力；二是即使改造后，正式容量规划也应该以压测实测值为准，而不是直接采用理论计算值，理论值只能作为规划起点，不能作为最终依据（这也印证了文档里"最终值必须以目标环境压测校准"这句话的必要性）。
