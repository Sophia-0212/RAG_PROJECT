In-Flight Requests（在飞请求数） ?Gauge（仪表盘指标）当前正在处理、还没返回结果的请求数量。数值是"此刻的存量状态"，不是累计值——请求处理完就会 -1。

面试常问的区别点：In-Flight ≠ QPS。QPS 是"每秒新增多少个请求"（流量），In-Flight 是"这一刻有多少个还没处理完"（存量）。两者关系近似 Little's Law：In-Flight ≈ QPS × 平均处理耗时。同样 QPS=10，如果处理耗时从 0.1s 涨到 5s，In-Flight 会从 ~1 暴涨到 ~50——这是请求堆积的典型信号。

基准怎么定的：基准 = 27.7（文档"3 Pod×12并发=36槏位，保守估算约27.7个在飞请求"，也就是占用率 ~77%）。告警门槏设在占用率 85%（≈30.6），危险门槏设在占用率 95%（≈34.2，逼近 36 槏位上限）——这两个阈值直接对应下方 capacity 拒绝真正开始触发的临界点，不是随便取的百分比。

QPS（每秒请求数） ?Counter（计数器）→ rate() 转速率底层指标 rag_requests_total 是一个只会往上涨的累计计数器，单看总数没有意义。Prometheus 用 rate(rag_requests_total[1m]) 把它换算成"每秒新增多少"——方括号 [1m] 是"取样窗口"，不是单位：意思是拿最近 1 分钟内这个计数器涨了多少，除以 60 秒，得到这 1 分钟的平均每秒速率，最终结果单位仍然是"次/秒"（req/s），跟窗口取多长完全无关。这是 PromQL 里最容易搞混的一点：[1m]只决定"用多长的历史窗口去平滑这个速率"，不改变输出单位。这也是为什么本面板顶部卡片用 [1m]（更灵敏，10 秒内的波动都能看出来）、下方折线图的说明里提到的告警规则常用 [5m]（更平滑，避免单次抖动误报）——同一个指标，取样窗口选多长取决于"要多灵敏还是要多稳"，是一个真实的工程取舍，不是随便选的。面试英文表达：throughput / requests per second (QPS)。

P95 Latency（P95 延迟） ?Histogram（直方图指标）真实 Prometheus 里 P95/P99 不是直接存出来的，是用 histogram_quantile(0.95, sum(rate(rag_request_duration_seconds_bucket[5m])) by (le)) 从一组预设边界的 _bucket{le="..."} 计数器里线性插值估算出来的，精度取决于 bucket 边界分得够不够密——这是近似值，不是精确值。

好处是可以跨多个 Pod/实例聚合（sum by (le) 直接把各实例的 bucket 加起来）；缺点是精度受限。面试常问的对照点：Prometheus 还有个 Summary 类型能算出精确分位数，但 Summary 的分位数是客户端本地算好的，没法跨实例聚合——这是 Histogram vs Summary 的经典权衡。

基准怎么定的：基准 = 3.08s（文档"上线后 RAG P95 完整响应 3.08 秒"，这是实测数字不是拍脑袋）。告警门槏 1.5× 基准（≈4.6s，正好逼近文档"基线"4.85s——也就是告警意味着"退回到优化前的水平"）；危险门槏 2.5× 基准（≈7.7s，接近 LLM 硬超时 llm_timeout_seconds=20s 的三分之一，用户体感已经很差）。

Average Latency（平均处理耗时） ?Histogram 的 sum/count（rate 后相除）PromQL 写法：rate(rag_request_duration_seconds_sum[5m]) / rate(rag_request_duration_seconds_count[5m])——用"耗时总和的增长速率"除以"请求数的增长速率"，就是滑动窗口内的平均耗时。跟 P95/P99 不同，这是精确计算，不是分位数插值估算。

为什么要跟 P95 放在一起看：Average 会被少数很快的请求拉低，掩盖长尾慢请求；P95/P99 才反映真实的用户体感下限。两者一起看，才能同时判断"整体水位"和"有没有极端慢请求"。也是 In-Flight 卡片提到的 Little's Law 里"平均处理耗时"这一项的真实来源——In-Flight ≈ QPS × Average Latency，本面板的 In-Flight 数值就是照这个公式算出来的，不是凭空模拟。

基准线一览表（Baseline Reference Table） ?"基准"是什么意思这里的"基准"（baseline）不是随便定的门槏，是系统在正常上线后、没有故障时的真实运行水位——本面板全部取自 test/002_1. 模拟业务背景与结果总览.md 里"上线后"这组实测数据（不是"基线"那组优化前的数字）。有了基准，才谈得上"现在这个数值算不算异常"——异常的定义就是"偏离基准多少"。

为什么用"基准×倍数"而不是每个指标手写一个固定区间：倍数法能显式表达"这个指标偏离正常水位的程度"，比如"P95现在是基准的2倍"这句话，比"P95现在是6160ms"信息量更大——后者你还要自己回想正常是多少，前者直接告诉你严重程度。真实 Prometheus 告警规则里，也经常用"当前值/基准值"这种比值（而不是绝对数值）来配置阈值，因为绝对数值会随流量规模变化，比值更稳定。

所有基准均来自"上线后"实测数据；告警/危险阈值按各指标业务含义单独设定倍数，不是统一套用同一个公式

QPS Trend（QPS 趋势） rate(rag_requests_total[1m]) ?为什么拆成 success / refused 两条线如果只看总 QPS，一次流量下跌可能是"用户变少了"（正常），也可能是"大量请求被拒绝了"（异常）。拆开看才能分清是需求侧变化还是服务侧出了问题。

refused 具体指哪些请求？举例：不是"处理失败"（那属于 error/exception），是连 RAG 流程都没真正跑起来、在最外层就被挡回去的请求，跟下方 Rejection Reasons 面板的四种 reason 一一对应：①某个租户当天发太猛，被令牌桶限速（quota）——比如一个客户脚本没做限流，1 秒内连发 50 次；②服务当前并发已经打满 36 个槏位，新请求进不来（capacity）——比如下游 LLM 突然变慢，大量请求卡在处理中；③同一个会话（conversation_id）被并发访问，比如用户在两个浏览器标签同时提问同一个对话（conversation_busy）；④协调服务（Redis）本身连不上了（coordination_unavailable）。这四种都是"服务主动挡在门口拒绝"，跟用户问题本身答不出来是两回事。

Latency Distribution（耗时分布） histogram_quantile(0.95, rate(..._bucket[5m])) 等 ? 为什么要同时看 Average/P50/P95/P99Average（平均耗时）容易被少数很快的请求拉低，看起来"很正常"；P50（中位数）代表大多数用户的真实体验；P99 代表最慢的 1% 用户有多惨。Average 正常但 P99 飙高，说明存在少数"极端慢请求"（比如某个租户的复杂查询、某次 GC 停顿），只看平均值会完全掩盖这类问题。

四条曲线各自变慢，通常意味着什么：
• Average 涨——整体请求的"平均水位"在抬升，通常是系统性、持续性的原因：下游依赖（LLM/Milvus）整体变慢、机器资源（CPU/内存）不够用了、流量比平时大很多导致排队。特点是"大家都慢一点"，不是个别请求特别惨。
• P50 涨——一半以上的请求都变慢了，比 Average 涨更能确认"这不是个别慢请求拉高平均值，是主流请求本身就慢了"。常见原因：数据库/向量库索引失效或查询计划变差、缓存命中率骤降、某个公共依赖（比如鉴权、限流组件）本身变慢，拖慢了每一个请求的固定开销。
• P95 涨——"尾部"用户开始受影响，但主流用户可能感知还不明显。常见原因：并发接近上限导致排队时间变长（对应 In-Flight 逼近 36 槏位）、GC（垃圾回收）停顿变频繁、少数租户的复杂查询（检索候选多、需要多轮改写）占比上升。这是最常被用来定 SLO 阈值、配置告警的一条线，因为它比 P50 更早暴露"局部恶化"，又不像 P99 那样容易被极端个例干扰。
• P99 涨——只有最慢的 1% 在恶化，Average/P50/P95 可能完全正常。常见原因：极少数"坏请求"（超长文本、命中了某个未优化的边界情况、触发了 execution.py 里的重试上限走了好几轮才失败）、单台机器/单个 Pod 局部故障（比如某个 Pod 磁盘 IO 抖动，只影响落在这台机器上的请求）、网络抖动的偶发超时重连。P99 单独涨、其余三条不动，通常不是"整体扩容"能解决的，得去挖具体是哪一小撮请求在拖后腿。

Rejection Reasons（拒绝原因分布） rate(rag_request_rejections_total[1m]) ?五种拒绝各自意味着什么quota（配额限流）：某个租户发得太猛，被令牌桶限速——这是随时间平滑发生的，跟此刻并发多少无关；capacity（容量超限）：整个服务并发槽位（36 个）被占满了才会触发，是纯瞬时的阈值行为，槽位没满时几乎不会发生；conversation_busy（会话占用中）：同一个会话被并发访问，协调层拒绝了；coordination_unavailable（协调服务不可用）：协调服务本身连不上了；circuit_open（熔断跳闸）：LLM 连续失败达到阈值（circuit_failure_threshold=3），熔断器直接拒绝，不再浪费时间去调一个已知挂了的依赖——这是本面板里唯一一种“延迟反而更低”的拒绝，因为它是快速失败，不用等超时。同样是“被拒绝”，触发机制、根因和该找谁修完全不同。

本面板里 capacity 的模拟方式：由 In-Flight 相对 36 个槽位的占用率派生，占用率超过 85% 才开始陡增，之下几乎为 0——不是像 quota 一样的持续背景噪声。

Idempotency / Duplicate Submits（幂等 / 重复提交） rate(rag_run_events_total[1m]) ?duplicate 暴增≠出 bug它只代表"同一个 request_id（请求幂等键）被重复提交了"，本身是幂等（idempotency）机制在正常拦截重复计算。真正要看的是它是不是伴随着延迟指标（P95/P99）同时上涨——那才说明根因是下游变慢导致客户端超时重试（client-side timeout retry），duplicate 只是这个根因的"副作用信号"，不是根因本身。

created 为什么也会跟着变：下游变慢时，新请求也会因为排队、用户等待体验变差而受到抑制，故障期间 created 通常会略有下降，不只是 duplicate 单向暴增——一次故障往往牵动多个相关指标，不是只影响一条曲线。

action="submit" 时按 outcome 拆分：created（全新请求）/ duplicate（幂等命中，重复提交）· 基准来自：重复副作用事故基线 2 次/月 → 上线后连续 5 个月为 0
created（全新请求） duplicate（重复提交）

Recovery Outcomes（恢复流程结果分布） rate(rag_run_events_total{action="recovery"}[1m]) ?为什么恢复要单独重新鉴权（re-authorization）被恢复的请求可能是很久以前中断的，这段时间用户权限可能已经变了（被收回、租户被禁）。所以恢复时不能沿用旧的鉴权结果，必须重新问一次权威系统（IAM，Identity and Access Management）。authorization_denied 说明重新问过后确实不再允许了，这个请求会被永久终止（terminal failure），不会再重试。

三者关系：本面板里 success/denied/retry 是从"本轮恢复尝试总量"按比例拆分出来的三个互斥分支，不是三条各自独立的曲线——它们理应此消彼长，故障期间 retry 占比会显著升高（下游还没恢复，重试大概率还是失败）。
