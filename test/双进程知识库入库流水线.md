# 双进程知识库批量入库流水线：解析进程与写入进程解耦

简历原句：参与开发双进程知识库批量入库流水线，解析进程与写入进程并行解耦，支持海量文档批量增量写入。对应代码：[documents/write_milvus.py](../documents/write_milvus.py)、[documents/milvus_db.py](../documents/milvus_db.py)。

---

## 核心思路：生产者-消费者模型

两个进程通过 `multiprocessing.Queue` 解耦：

```
进程1（解析，CPU密集）──put(批次)──> Queue(maxsize=20) ──get()──> 进程2（写入，IO密集）
```

**进程1 `file_parser_process`**：扫目录拿 md 文件 → `MarkdownParser` 逐个解析 → 攒够 20 条（`batch_size`）就 `put` 进队列，缓冲区清空继续攒下一批。文件遍历完，剩余不足批次的也 `put` 一次，最后放 `None` 当终止信号。

**进程2 `milvus_writer_process`**：起自己的 Milvus 连接（`MilvusVectorSave`，embedding + BM25 都在这层）→ `while True` 死循环 `queue.get()`（阻塞式，不用轮询耗 CPU）→ 拿到列表就 `add_documents` 写库 → 拿到 `None` 就退出循环。

主进程只干三件事：建 collection、fork 两个子进程、`join()` 等结束。

---

## 面试要点

### 为什么拆两个进程，不用一个循环顺序处理

解析是 CPU 密集（Unstructured 解析 md + 语义切块跑 embedding 模型），写入是 IO 密集（网络请求 Milvus）。顺序执行等于两段时间相加；拆成两个进程后，绕开 Python GIL 的进程内限制，两边真正并行——解析下一批的同时上一批已经在写库路上，整体吞吐取决于较慢的那一段而不是总和。

### 队列的背压作用

`Queue(maxsize=20)` 有界队列做背压：写入进程被 Milvus 网络延迟拖慢时，队列满了 `put` 会阻塞解析进程，天然限流，不会无限攒积压把内存打爆——海量文档场景下的必要保护。

### 批处理粒度

攒 20 条才发一批，而不是逐条发送——减少队列 put/get 调用次数和跨进程序列化开销，同时不会因为攒太大导致写入方等待过久，20 是吞吐和延迟的折中。

### 终止信号设计

用 `None` 作为哨兵值（sentinel）告诉消费者"生产者结束了"，多进程队列的标准终止协议，不需要额外信号量或共享状态。

### "增量写入"具体指什么

写入进程只是 `add_documents`，不做删除重建，配合 Milvus 的 `auto_id=True` 自增主键，新文档直接追加，不影响已有数据——区别于 `create_collection()` 那种破坏性重建（先 drop 再建）。

## 追问记录

### Q1：什么是背压？

背压（backpressure）：下游处理慢时，反向抑制上游生产速度的机制。

本项目例子：[write_milvus.py:87](../documents/write_milvus.py#L87) `Queue(maxsize=20)`。

```
解析进程 put() → [队列容量20] → get() 写入进程
```

Milvus 写入慢（网络延迟/批量插入耗时）时，队列很快堆满 20 条。这时解析进程再调 `put()` 会**阻塞**——不是丢弃，是硬等，直到写入进程 `get()` 腾出空位。写得慢 → 队列满 → 解析被迫停下等 → 解析也变慢，速度被下游"压"回上游，故名背压。

没背压会怎样：换成无界队列（`Queue()` 不设 `maxsize`），解析进程会一直狂 `put`，不管写入进程跟不跟得上，内存里堆积的 Document 对象越滚越多，海量文档场景直接内存溢出（OOM）。

一句话：`maxsize` 参数就是背压阀门，让快的一边等慢的一边，拿内存安全换取速度自动匹配。

### Q2：CPU密集是什么？IO密集是什么？

CPU密集：耗时主要花在计算上，CPU一直算，等不着别的。例：切词、算embedding向量（矩阵运算）、语义相似度计算。

IO密集：耗时主要花在等——等磁盘、等网络返回，CPU大部分时间空闲。例：查数据库、调HTTP接口、读写文件。

区分点：CPU密集用多进程才能真并行（绕开GIL）；IO密集用多线程/协程就够（等待时GIL会释放）。项目里解析进程跑embedding模型属CPU密集，写入进程等Milvus网络返回属IO密集，两类混一个进程里顺序跑最亏，拆开才能叠起来跑。

### Q3：Unstructured是什么，是第三方库吗？谁提供的？

第三方库，`pip install unstructured`，公司 Unstructured.io 做的开源库。专门干"把各种格式文件（PDF/Word/HTML/Markdown等）解析成结构化元素"这件事。

项目里 [documents/markdown_parser.py](../documents/markdown_parser.py) 用了它的 `UnstructuredMarkdownLoader`（LangChain 对 Unstructured 库的封装），`mode='elements'` 参数让它把一篇 md 拆成 Title、NarrativeText 等带 `category` 标签的元素列表，而不是整篇当一个字符串——后续 `merge_title_content()` 按标题层级合并，靠的就是这些 category 标签。

### Q4：Milvus不是本地docker运行的吗，为什么需要网络请求？

看 [utils/env_utils.py](../utils/env_utils.py)，`MILVUS_URI` 硬编码 `http://1.95.116.112:19530`——这是**远程服务器上的 Milvus**，不是本机 localhost，是走公网/内网的真实 HTTP 请求。

即便 Milvus 跑在本地 docker 里（`http://localhost:19530`），"网络请求"这个说法依然准确——docker 容器和 Python 进程是两个独立进程，即使同机，SDK 到 Milvus server 走的还是 TCP/HTTP 协议栈（走 loopback 网卡），不是进程内函数调用。这跟"是不是同一台物理机"无关，关键是"跨进程边界、走协议通信"就算IO/网络操作，耗时模式（建连接、序列化、等响应）跟真正跨机器请求是一致的，只是本机延迟通常更低。

本项目这个具体场景，`MILVUS_URI` 指向远程机器 `1.95.116.112`，是真实跨机器网络请求，延迟比本地 docker 更明显。

### Q5：GIL是什么？"进程内限制"是什么？是一个完整术语吗？

不是一个完整术语，是两个概念揍一块儿了。

**GIL（Global Interpreter Lock，全局解释器锁）**：CPython（标准Python实现）自带的一把全局锁。规则：一个进程内，任一时刻只有一个线程能执行Python字节码，哪怎机器有8核，同进程内开8个线程，也只有1个线程真正在跑，其他7个干等。

**"进程内限制"不是术语，是说明**——GIL锁的作用范围是"进程内"。GIL 是进程级的锁，每个进程有自己独立的一把 GIL，互不影响：

- 同一进程内开多线程 → 抢同一把GIL → CPU密集任务多线程等于没并行，白搭
- 开多个进程 → 每个进程一把独立GIL → 真正吃满多核，并行生效

**为什么IO密集任务多线程反而没事**：线程等网络/磁盘返回时会主动释放GIL给别的线程用，等IO结果那段时间反正闲着，让别的线程插空执行。所以IO密集用多线程没问题，CPU密集（一直占着CPU算）用多线程才是真瓶颈——没有"等待"的空隙让别人插队。

对应到项目：[write_milvus.py](../documents/write_milvus.py) 用的是 `multiprocessing.Process` 不是 `threading.Thread`——如果解析进程和写入进程改成同进程内的两个线程，解析那部分（跑embedding模型，纯CPU算）会被GIL锁死，写入线程等网络的空闲时间也帮不上解析线程的忙，两边挤同一把锁，等于白拆。用 `Process` 各自独立进程各自独立GIL，才能让CPU密集的解析真正利用到另一个核，跟写入进程同时跑。

### Q6：IO密集多线程为什么"没问题"？是不是"不竞争GIL的线程"和"竞争GIL的线程"分两类？

不是。常见误解是以为"有些线程天生不需要GIL"，实际是**所有线程都需要GIL，区别在于IO密集的线程会在遇到IO操作时主动把GIL让出去**。

正确顺序：

```
线程A: 抢到GIL → 跑Python代码 → 遇到 socket.recv()（等网络）→ 主动释放GIL → [此时不占用GIL，纯等待]
                                                                    ↓
线程B:                                            这段空档 抢到GIL → 跑它的Python代码
                                                                    ↓
线程A: 网络数据回来了 → 重新去抢GIL → 抢到后继续跑后面代码
```

关键纠正：不存在"不竞争GIL的线程"。所有线程本质上都要抢同一把锁，区别只是——**CPU密集的线程死死攥着GIL不放**（一直在算，没有天然的释放时机）；**IO密集的线程算一小段就遇到IO，主动松手**，把GIL让给别人用一会儿，自己去纯等待，等完了再回来抢。

这就是为什么IO密集多线程有效：因为有"主动让锁"的动作，多个线程能轮流用这把锁，总体上没人在空耗CPU。而CPU密集没有这个让锁动作，谁抢到就一直用到时间片耗尽才被抢，本质上还是串行执行，只是操作系统层面在多个线程间来回切换、开销更大，还不如单线程。

### Q7：面向面试，讲一下从单进程到双进程的演进背景（为什么需要优化）

**面试话术：**

最早的知识库入库脚本是单进程顺序执行的：读一个 md 文件 → 解析 → 切块 → 调 embedding 模型算向量 → 写 Milvus，写完再读下一个文件，一条线走到底。

问题出在批量导入的场景——知识库要接入几百上千篇文档做初始化灌库，单进程跑起来发现整个流程慢得不成比例。定位下来，耗时分两段完全不同性质：

- 解析+切块这段是CPU密集，Unstructured解析文档结构、语义切块要跑embedding模型算向量，这段CPU一直在算；
- 写入Milvus这段是IO密集，一次网络请求打过去，等Milvus那边建索引、落盘返回结果，这段CPU基本闲着，纯粹在等网络。

单进程顺序执行的问题就在这——**CPU密集和IO密集这两段完全没有重叠，是严格串行的**。解析第10篇文档的时候，写第9篇文档的网络请求早就该发出去了，但因为是同一条执行流，必须等上一步的Milvus写入彻底返回才能开始下一步的解析，等待网络返回的这段时间，CPU完全被浪费掉，没有干任何有用的事。

批量导入几百篇文档，这种"计算-等待-计算-等待"的串行模式会把两段耗时简单相加，规模一大延迟就线性劣化，几百篇文档跑下来动不动小时级。

优化思路很直接：**把两段解耦成流水线，让计算和等待重叠起来**。拆成两个进程，一个专职解析（吃CPU），一个专职写入（吃网络IO等待），中间用队列传数据。解析进程不用等上一批写完就能继续解析下一批，写入进程也不用等下一批解析完才能写——两条线各自往前跑，谁也不卡谁，只要队列没满没空。理论上总耗时从"解析时间+写入时间"降到"两者中较长的那一个"，规模越大这个收益越明显。

之所以选多进程不是多线程，是因为解析这段是CPU密集操作，Python的GIL会让同进程内的多线程在CPU密集任务上没有真正并行的效果，必须用多进程才能吃到多核的并行收益。

队列这块还顺手解决了内存问题——如果不限制队列大小，一旦写入端被网络波动拖慢，解析端产出的数据会不断堆积在内存里，批量场景很容易把内存打满。给队列设置容量上限做背压，让解析端在队列满时自动停下来等，避免了这个隐患。

**面试官常见追问，提前想好：**

- **"怎么发现慢的，有具体数据吗"**：老实说这里更多是理论定位（分析代码执行流程发现是串行结构问题），别编"用profiler测出xx秒"这种没做过的细节。如果被问到，诚实回答"当时是通过代码逻辑分析判断出串行瓶颈，没有留存具体的性能测试数据"——比编数字安全。
- **"为什么按CPU/IO这个维度拆，不是按文件分片开多进程"**：因为瓶颈的性质不同，按性质分工比按数据分片更能形成流水线重叠效果；如果按文件分片开N个进程各自独立解析+写入，没有流水线重叠，只是并发度增加，且会有N个Milvus连接同时抢写，不如生产者-消费者模型可控。
- **别编团队叙事**：别把背景讲成"我们组遇到性能问题，领导要求优化"这种编造场景，简历项目通常是个人/学习项目，讲成"批量导入场景下自己发现串行执行效率低，主动做的架构优化"更真实可信。

## 老实说：当前实现的短板（面试深挖会被问到）

- **没有真正的去重判重**：同一文件重复跑会产生重复向量，没有基于 source/hash 的幂等逻辑。简历里"增量"只能讲成"追加写入不重建 collection"，不能扩大成"支持去重/幂等"。
- **单生产者单消费者**：只有一个 `None` 终止信号，因为只有一个消费者在读。别说成多消费者模型，否则会被追问"两个消费者怎么分终止信号"。
- **错误处理简单**：解析失败 `log.exception` 后跳过继续，没有重试/死信队列，海量批处理场景这个属于"已知优化点"而非"已实现能力"。
- [write_milvus.py](../documents/write_milvus.py) 里 `md_dir` 目前是相对路径写法（已修正过 Windows 硬编码问题），可以提一句路径是可配置的。
