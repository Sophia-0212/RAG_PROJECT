## 2. 模拟总体架构

```
CRM Web / IM / OpenAPI
        |
API Gateway + SSO
认证、租户、限流、trace
        |
+-------+---------------------------+
|                                   |
ONECRM Domain API              Dify Control/Runtime
客户档案与业务规则             应用、工作流、版本、节点
|                                   |
|                          +--------+--------+
|                          |                 |
|                    Approval Service    RAG Service
|                    审批状态与恢复       LangGraph
|                          |                 |
|                    Task Center        Retrieval Gateway
|                    通知与审计         dense + sparse
|                          |                 |
+-------------------- Tool Gateway          Milvus
                      授权、Schema、幂等      |
                           |              Reranker
                    CRM Action APIs          |
                                           Model Gateway

横切能力：PostgreSQL、Redis、Kafka、配置中心、OpenTelemetry、日志、指标、审计库
```

核心边界：

- ONECRM 是客户数据与业务不变量的唯一 owner。
- Dify 负责应用层可配置编排，不保存 RAG 内部迭代状态。
- LangGraph 负责检索状态机，不直接决定企业权限。
- Approval Service 保存长时审批状态，不依赖 Dify worker 存活。
- Tool Gateway 对每次动作重新鉴权、校验参数并注入幂等键。

### 2.1 RAG Service 共享状态面

```
Gateway / Dify
      |
RAG Service（3 Pods，每 Pod 1 worker）
      |-- PostgreSQL：request run ledger、LangGraph checkpoint、幂等 turn、会话归属/摘要/TTL
      |-- Redis：同会话 lease、租户级原子限流、清理任务选主
      |-- Milvus：受 tenant/ACL/有效期约束的知识检索
```

三个 Pod 无需会话粘滞：任意 Pod 都从 PostgreSQL 恢复状态；Redis 保证同一 tenant + conversation 同时只有一个执行者。Redis 故障时返回稳定 503，不能退化成本地锁。SQLite 仅保留为开发环境单进程后端。

新增两个独立 recovery worker。API 先按 `(tenant_id, request_id)` 持久化运行并取得 fencing token；Pod 异常退出后，worker 等 PostgreSQL lease 过期再接管，重新向 IAM 获取 principals，并按 snapshot 分别执行“重放最小输入、`invoke(None)` 续跑 pending、直接提交完整结果”。新一轮会话请求不能越过尚未终止的旧运行。
