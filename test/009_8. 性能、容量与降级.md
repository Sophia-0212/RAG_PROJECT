## 8. 性能、容量与降级

### 8.1 延迟预算

| 阶段 | P50 | P95 |
| --- | --- | --- |
| 身份/权限 | 8ms | 18ms |
| Query rewrite | 110ms | 240ms |
| Dense + Sparse 并行召回 | 42ms | 91ms |
| 融合与去重 | 6ms | 16ms |
| Rerank | 82ms | 170ms |
| 生成完整答案 | 1.12s | 2.05s |
| Claim 校验 | 170ms | 420ms |
| 平台与网络开销 | 95ms | 210ms |
| 端到端 | 1.76s | 3.08s |

P95 不能由各阶段 P95 直接相加，因为请求分布和并行阶段不同；端到端以 trace 实测。

### 8.2 容量保护

- workspace 级并发、QPS、日 Token 和单流程节点数配额。
- 单运行最大 60 个节点、最长 15 分钟；审批等待不计执行时长。
- RAG 最大 2 次检索重试、1 次生成重试、6 秒 deadline。
- 队列按租户加权公平，单租户最多使用 30% worker。
- 模型网关使用 200ms/500ms/1s 指数退避加 jitter，总重试不超过一次。
- 高错误率时熔断模型或 reranker，避免重试风暴。

### 8.3 降级矩阵

| 故障 | 降级 |
| --- | --- |
| Rewrite 模型超时 | 原问题 + 最近已确认实体 |
| Dense 服务失败 | Sparse only |
| Sparse 服务失败 | Dense only |
| Reranker 超时 | RRF 排名 |
| 生成主模型失败 | 经过 schema 回归的备用模型；高风险问题拒答 |
| Evaluator 超时 | 低风险带提示返回，高风险拒答/转人工 |
| Milvus 不可用 | 已验证 FAQ 缓存，否则明确不可用 |
| ACL 服务异常 | 高敏检索与动作 fail closed |
| 审批中心异常 | 已持久化任务等待恢复，不绕过审批 |
| PostgreSQL 状态面异常 | readiness 失败，停止有状态执行，不生成未跟踪状态 |
| Redis 协调异常 | fail closed，返回 `COORDINATION_UNAVAILABLE`，不退回本地锁 |

### 8.4 多副本容量基线

- 初始 3 Pod、每 Pod 1 worker、12 个本地并发槽位，总应用槽位 36；HPA 范围 3-9。
- PostgreSQL API 每 Pod 连接池最小 1、最大 16，3 Pod 上限 48；2 个恢复 Worker 每 Pod 上限 4，总应用上限 56；Schema/清理 Job 与运维连接必须额外预留。
- 单 Pod semaphore 保护本实例资源；Redis 令牌桶保证跨 Pod 租户公平；二者职责不同。
- PDB `minAvailable=2`、滚动发布 `maxUnavailable=0`，跨可用区强约束、跨节点软反亲和。

这些值与模拟 9 QPS 场景匹配，仍是初始配置。需用共享状态负载报告观测吞吐、P50/P95、池等待和错误分布后调整。

恢复 Worker 与 API 分池、分并发、分副本。积压时不无限增加尝试：默认恢复窗口 300 秒、最多 3 次并指数退避；监控最老积压时间、重复模型调用成本和对正常请求 P95 的影响，再决定是否扩 Worker。
