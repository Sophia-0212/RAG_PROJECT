# 检索工具封装 + 会话维度多轮对话历史管理 — 面试讲解

## 背景

CRM 领域知识库，销售/客服场景连续追问多（如先问"价格异议怎么处理"，接着追"那如果客户要求打折呢"），单轮 QA 不够，需要记住上下文。

对应简历描述：
> 封装检索工具供 Agent 调用，实现基于会话维度的多轮对话历史管理，支撑销售/客服连续追问场景。

## 1. 检索工具封装（`tools/retriever_tools.py`）

把 Milvus 检索器包成 LangChain 标准 Tool，让 Agent 能"按需调用"而不是每次都强制检索：

```python
mv = MilvusVectorSave()
mv.create_connection()
retriever = mv.vector_store_saved.as_retriever(
    search_type='similarity',
    search_kwargs={
        "k": 4,
        "score_threshold": 0.1,
        "ranker_type": "rrf",
        "ranker_params": {"k": 100},
        'filter': {"category": "content"}
    }
)

retriever_tool = create_retriever_tool(
    retriever,
    'rag_retriever',
    '搜索并返回关于 "CRM系统" 的信息, 内容涵盖：销售SOP流程、产品功能模块、系统操作与故障排查、客户异议处理话术等'
)
```

- `create_retriever_tool` 把 retriever 包装成 `rag_retriever` 工具，附带工具描述文本。这段描述就是 Agent 做 tool selection 时判断"要不要调用"的依据。
- retriever 底层走 Milvus 混合检索：dense（BGE embedding）+ sparse（BM25），`ranker_type: rrf` 做召回融合排序，`k=4` 取 top4，`filter={"category":"content"}` 做元数据过滤（排除标题类等非正文块）。
- **工具化的意义**：把检索能力做成可复用、可插拔的原子能力，Agent 层不用关心 Milvus 细节，只需要拿到一个描述清晰的 Tool，模型自己决定"这个问题要不要查知识库"。

## 2. Tool-calling Agent（`agent/rag_agent.py`）

```python
prompt = ChatPromptTemplate.from_messages([
    ('system', '你是一个智能助手，尽可能的调用工具回答用户的问题'),
    MessagesPlaceholder(variable_name='chat_history', optional=True),
    ('human', '{input}'),
    MessagesPlaceholder(variable_name='agent_scratchpad', optional=True),
])

agent = create_tool_calling_agent(llm, [retriever_tool], prompt)
executor = AgentExecutor(agent=agent, tools=[retriever_tool])
```

- `create_tool_calling_agent` 用 LLM 原生 function-calling 能力驱动，模型看到用户问题和工具描述，自主决定是否调用 `rag_retriever`，调用后把检索结果拼回上下文继续生成。
- Prompt 关键点：`MessagesPlaceholder('chat_history')` 放历史对话，`MessagesPlaceholder('agent_scratchpad')` 放 Agent 中间的工具调用轨迹（ReAct 式 thought/action/observation）。

## 3. 会话维度历史管理（`RunnableWithMessageHistory`）

```python
store = {}

def get_session_history(session_id: str) -> BaseChatMessageHistory:
    if session_id not in store:
        store[session_id] = ChatMessageHistory()
    return store[session_id]

agent_with_history = RunnableWithMessageHistory(
    executor,
    get_session_history,
    input_messages_key='input',
    history_messages_key='chat_history'
)

agent_with_history.invoke(
    {'input': '客户对价格有异议该怎么处理？'},
    config={'configurable': {"session_id": 'zs123'}}
)
```

- 核心是 `RunnableWithMessageHistory` 包装 `AgentExecutor`，指定：
  - `input_messages_key='input'`：本轮用户输入放哪个 key
  - `history_messages_key='chat_history'`：历史消息注入 prompt 哪个占位符
- **会话隔离**通过 `get_session_history(session_id)` 实现：内存字典 `store`（`session_id -> ChatMessageHistory`），调用时 `config={'configurable': {'session_id': 'zs123'}}` 传入会话 ID，框架自动按 session_id 取/建历史对象，追加本轮消息。
- 效果：同一个 `session_id` 下多轮调用，历史自动累积注入 prompt，模型能理解"这个""那个"之类的指代和上下文追问；不同 session_id 完全隔离，不会串话。

## 一句话总结话术

> 我把 Milvus 混合检索封装成 LangChain Tool 交给 tool-calling agent 自主调度，再用 RunnableWithMessageHistory 按 session_id 维度管理对话历史，实现销售/客服场景下的连续追问能力。

## 局限性（面试官追问时诚实作答，加分项）

- 当前 `store` 是进程内内存字典，重启即丢，没做持久化（Redis/DB），生产场景要换成持久化的 `BaseChatMessageHistory` 实现。
- 没做历史长度截断/摘要，长会话会让 prompt 越滚越大，可提历史窗口裁剪或摘要压缩作为优化方向。
- 检索环节本身没根据历史做 query rewrite（graph2 pipeline 里有 `transform_query` 这类改写机制，可对比讲，展示对两条 pipeline 差异的理解）。
