# RAG评估实战报告：graph1 vs graph2 召回率与生成质量对比

面试官问"你说的召回率提升多少，这个数字怎么来的"——这份报告是这个问题的完整答案。按吴师兄《RAG评估从0到1》一文的六步方法论实操一遍：测试集构建→检索层评估→生成层评估→问题定位→A/B对比→面试话术。

配套文件：[recall_eval/](./recall_eval/)（12篇自建文档、40题评测集、交叉验证记录、三层评估脚本、全部原始结果JSON）

---

## 第一步：测试集构建

### 评估范围

12篇自建CRM文档，覆盖4大场景：销售SOP流程（2篇）、客户异议处理（4篇）、产品功能说明（4篇）、故障排查手册（3篇，其中1篇归入产品/异议交叉），每篇≥3000字，共写入独立Milvus collection `interview_recall_test`，与生产collection`t_collection01`完全隔离，切块后共39个`category=content`的chunk。

### 设计评估问题

**问题来源**：全部人工编写（40题），未采用"LLM生成候选+人工筛选"的组合方案——这是跟文章方法论的主要差异点，规模（40条 vs 文章的200+条）和生成方式都更轻量，原因是聚焦在"验证graph1/graph2差异是否存在、差异体现在哪个指标"这个具体问题，不追求覆盖度意义上的生产级评测集。

**四种问题类型**（按文章方法论补齐）：

| 类型 | 数量 | 示例 |
|---|---|---|
| factual（简单事实题） | 24 | "报价折扣力度在什么范围需要销售总监二级审批？" |
| negation（否定性查询） | 9 | "普通销售看不到别的同事的客户数据，这个不是bug对吧？" |
| multi_hop（多跳推理题） | 4 | "客户签合同后，销售大概要跟进多久才能确认这个客户不会轻易流失？"（需综合同一文档内5个维护节点） |
| colloquial（口语化查询） | 3 | "一个大客户同时要销售、技术顾问、法务一起跟，这种情况下商机归属和权限应该怎么分配？" |

三题跨文档多跳（题38-40）额外验证了"需要综合两篇不同文档才能完整回答"的场景（如折扣审批走CRM流程+合同条款走法务流程，分别来自01和10两篇文档）。

### 标注参考答案和支持证据

每题标注`ground_truth_source`（标准答案所在文档，多跳题可以是2篇）、`ground_truth_snippet`（原文关键片段，用于人工核实忠实度）、`reference_answer`（人工撰写参考答案，供生成层LLM-as-a-Judge比对）。

### 质量审查（交叉验证）

用独立subagent对40题做了100%交叉核对（超过文章建议的20%抽样比例），核对四项：snippet是否能在文档原文找到、reference_answer是否有编造内容、question_type分类是否准确、是否存在重复题。

**发现问题**：40题中1题（2.5%）存在ground_truth标注错误——题1"线索超过多久没跟进会退回公共池"，原标注为01号文档的"3个工作日内补全信息"规则，交叉验证发现真正答案是04号文档的"72小时无跟进记录"规则（两条规则文字表述相似但触发条件不同，容易搞混）。已修正标注并针对该题重跑了全部三层评估。

**对比文章基准**：文章提到"初次标注错误率约8%，交叉验证后降到2%以下"，本次实测错误率2.5%，接近该区间下限，说明标注质量整体可靠，snippet真实性和reference_answer忠实度100%通过核查。

## 第二步：检索层评估

### 指标定义与结果

| 指标 | 结果 | 说明 |
|---|---|---|
| Milvus检索层Recall@k（完全命中，多跳题要求全部ground truth文档都命中） | 100% (40/40) | 检索本身没有漏掉任何标准答案文档 |
| Milvus检索层Recall@k（部分命中，至少命中一篇） | 100% (40/40) | 同上 |
| MRR（Mean Reciprocal Rank） | 0.9458 | 平均而言，第一个命中结果排在1.06位左右，排序质量很高 |
| NDCG@4 | 1.4619 | 大于1是因为部分题目ground truth在top4里出现了多次（同一文档被检索出多个chunk），belongs在合理区间 |
| 冗余率（同一来源文档被重复检索的chunk占比） | 30.63% | 平均每题4个检索结果里约1.2个是"重复来源"，说明k=4的候选池里有一定比例的信息冗余 |

### graph1 vs graph2 过滤后的表现

| 指标 | graph1（整批判断） | graph2（逐chunk过滤） | 差值 |
|---|---|---|---|
| Recall@k（完全命中） | 100% (40/40) | 100% (40/40) | 0 |
| Precision@k（保留chunk中命中ground truth的比例，均值） | 49.38% | 74.79% | **+25.42个百分点** |

**按问题类型拆解Precision**（这是v2相比v1的新发现，v1只有24题的整体均值，没有按类型拆分）：

| 问题类型 | graph1 Precision | graph2 Precision | 差值 |
|---|---|---|---|
| factual（n=24） | 44.8% | 74.3% | +29.5pp |
| multi_hop（n=4） | 68.8% | 77.1% | +8.3pp |
| negation（n=9） | 58.3% | 87.0% | +28.7pp |
| colloquial（n=3） | 33.3% | 38.9% | +5.6pp |

**发现**：graph2的精筛优势在factual和negation类型题上最明显（+28~29个百分点），在multi_hop和colloquial题上优势收窄（+5~8个百分点）。原因推测：multi_hop题因为答案本身需要综合多个chunk，graph2逐chunk判断时容易把"部分相关但不完整"的chunk也判为相关保留下来（precision提升空间有限）；colloquial题因为提问措辞和文档原文差异大，检索本身召回的4个chunk里相关信号更弱，两条pipeline的判断都更容易出错，导致两者precision都偏低（33%-39%区间）且差距缩小。这跟"多跳/口语化查询更难处理"这一文章观点是吻合的实测证据。

## 第三步：生成层评估（v2新增，v1完全没测这一层）

这是本次相比v1最大的方法论补齐——v1只测到"过滤后剩哪些chunk"就停了，v2补上了文章第四部分讲的三个生成层维度：**correctness（正确性）、faithfulness（忠实度）、relevance（答案相关性）**，全部用手写LLM-as-a-Judge实现（不引入RAGAS等外部包，跟项目现有代码风格保持一致）。

流程：取graph1/graph2各自过滤后保留的chunk → 复刻`graph/generate_node.py`和`graph2/generate_node2.py`的生成prompt（两者完全一致，都是"根据上下文回答问题"）→ 分别生成答案 → 三个独立的LLM-as-a-Judge分别打分（每个维度单独一次LLM调用，避免同一次调用里多个维度互相干扰判断）。

### 汇总结果

| 指标 | graph1 | graph2 | 差值 |
|---|---|---|---|
| Correctness（正确性均值） | 98.58% | 98.28% | -0.30pp |
| Faithfulness（忠实度均值） | 97.97% | 97.97% | 0 |
| Relevance（答案相关性均值） | 96.35% | 94.93% | **-1.42pp** |

**这是本次实测最反直觉、最值得深挖的发现：生成层三个指标，graph2没有一个显著优于graph1，Relevance甚至graph2略低于graph1。**

### 为什么"检索层过滤更精细"没能转化成"生成层答案更好"

逐题核查差异最大的案例，找到了具体机制：

**案例（题10）**："商机从初步接触推进到需求确认阶段，需要满足什么条件？"标准答案要求两个信息点：①至少一次有效沟通记录（电话超3分钟或面谈）②系统会自动统计通话时长做强制校验。

- graph1保留了全部4个chunk（其中包含无关内容），但**碰巧**这4个chunk里完整包含了①②两个信息点，生成答案完整覆盖，relevance=1.0
- graph2精筛后只保留1个chunk（precision=1.0，非常"干净"），但这个chunk只包含①，遗漏了②"系统强制校验"这个次要信息点，生成答案relevance掉到0.6

**这暴露了一个关键机制**：graph2逐chunk判断"这个chunk跟问题相关吗"，判断粒度是chunk级二元决策，当标准答案需要的信息**分散在多个chunk**（哪怕都来自同一篇文档的相邻段落）时，如果其中某个chunk的相关性判断"踩线"（比如包含次要信息但主干信息不足），逐chunk判断可能会把它判为不相关而丢弃，导致最终传给生成环节的上下文反而比graph1"整批全留"更不完整。**graph1的"整批要或整批不要"策略在这种场景下，因为不做精细取舍，反而"误打误撞"保留了更完整的信息面**。

这跟第二步发现的"multi_hop/colloquial类型precision提升有限"是同一机制的两面：**graph2的精筛在信息高度集中于单个chunk的场景下（factual、negation类型题的大部分情况）优势明显，但在信息分散、需要多chunk拼接才能完整回答的场景下，精筛可能反而制造"漏筛"风险**。

### 生成层按问题类型拆解

| 问题类型 | graph1 Correctness/Faith/Relevance | graph2 Correctness/Faith/Relevance |
|---|---|---|
| factual（n=24） | 0.989 / 0.992 / 0.962 | 0.983 / 0.989 / 0.942 |
| multi_hop（n=4） | 0.938 / 0.945 / 0.942 | 0.963 / 0.935 / 0.950 |
| negation（n=9） | 0.994 / 0.961 / 0.979 | 0.984 / 0.983 / 0.970 |
| colloquial（n=3） | 1.000 / 0.987 / 0.953 | 1.000 / 0.953 / 0.940 |

有意思的是multi_hop题反而是graph2 correctness更高的唯一类型（0.963 vs 0.938）——因为多跳题本身需要综合多个信息点，graph2逐chunk判断"相关"的门槛相对宽松（"不需要非常严格的测试，目的是过滤掉错误的检索结果"，这是`grader_chain.py`里prompt原文的表述），在多跳场景下反而没有像factual题那样过度精简。

## 第四步：问题定位

按文章的分层诊断逻辑给出结论：

**检索层**：两条pipeline共享同一次Milvus检索，Recall@k 100%持平，说明检索本身（RRF混合检索+k=4）在这批测试语料规模下已经足够可靠，不是瓶颈。

**过滤层**：graph2逐chunk判断相比graph1整批判断，Precision提升25.4个百分点，这个差异是真实存在且可复现的（40题、100%交叉验证过的标注），证明"过滤粒度"这个设计差异确实有可观测的效果，方向与理论预期（`graph1_vs_graph2_doc_grading.md`里的分析）一致。

**生成层**：过滤层的Precision优势**没有**传导到生成层的Correctness/Faithfulness/Relevance指标上，三者graph2均未显著优于graph1，Relevance反而更低。**问题不在Prompt或模型能力（两条pipeline用的生成prompt完全相同），而在过滤策略本身的粒度权衡**——逐chunk判断在信息分散的题目上有"过度精简、漏掉次要但必要信息"的副作用，这个副作用恰好抵消了精筛在"减少噪音"上的收益。

用文章的话术模板套：**"检索效果好但生成效果差——说明找到了正确文档但LLM没用好，问题出在Prompt或模型能力"**——本次实测更精确的结论是：**检索效果好、过滤精度也更高，但生成效果没有随之提升，问题出在过滤策略的粒度权衡本身，不是Prompt或模型能力**，这是文章原有诊断框架里没有覆盖到的第四种情况，值得在面试里主动提出来展示深度思考。

## 第五步：A/B对比方法论说明

本次评测的A/B对比设计：
- **对照变量固定**：两条pipeline共享同一次Milvus检索结果（避免检索随机性造成不公平对比），只有"过滤逻辑"这一个变量不同
- **同一测试集跑两次**：40题在完全相同的输入条件下分别跑graph1和graph2的过滤+生成逻辑
- **显著性判断**：过滤层Precision差异25.4个百分点，跨越了24/4/9/3四种问题类型都保持一致方向（graph2全部≥graph1），可以判定为真实、稳定的效果差异；生成层三个指标差异在±1.5个百分点以内，且方向不一致（correctness/faithfulness基本持平，relevance graph2更低），不能判定为"graph2生成质量更好"。

## 第六步：面试怎么答（四段话术，基于本次真实数据）

**第一段——测试集构建（30秒）**："我构建了40条覆盖12篇CRM文档的测试集，人工编写并标注参考答案和支持证据片段，覆盖factual/multi_hop/negation/colloquial四种问题类型。做了一次全量交叉验证（超过通常20%的抽样比例），发现并修正了1处标注错误（2.5%错误率），跟行业实践里'交叉验证后错误率降到2%以下'的经验值接近。"

**第二段——分层评估（30秒）**："检索、过滤、生成三层分开评估。检索层两条pipeline共享同一次Milvus检索，Recall@k持平100%，说明检索本身不是瓶颈。过滤层graph2逐chunk判断比graph1整批判断，Precision提升了25个百分点，这个差异在四种问题类型上都稳定存在。但生成层——我们进一步做了正确性、忠实度、答案相关性三个维度的LLM-as-a-Judge评估，发现过滤层的精度优势并没有传导到生成层，三个指标graph2都没有显著提升，answer relevance甚至比graph1低了1.4个百分点。"

**第三段——工具与方法（20秒）**："没有引入RAGAS等现成框架，全部手写LLM-as-a-Judge逻辑，跟项目现有代码风格保持一致，也更方便控制评估的判断标准跟实际业务场景对齐。生成阶段复用了项目里graph1和graph2完全相同的生成prompt，确保对比的唯一变量是过滤策略本身。"

**第四段——实际发现与反思（30秒）**："这次评测最有价值的发现不是'graph2更好'这种简单结论，而是定位到了一个具体机制：graph2的逐chunk精筛在信息集中在单个chunk的题目上效果很好，但当标准答案需要综合多个chunk的信息时，逐chunk的二元判断可能会误判掉包含次要但必要信息的chunk，导致生成阶段拿到的上下文反而不如graph1'整批全留'更完整。这说明检索过滤的粒度设计需要结合实际问题的信息分布特征来选择，不是'越精细越好'，这是我们后续要考虑的优化方向——比如是否应该在逐chunk判断之外，增加一层'检查是否遗漏了标准答案所需的关键信息类别'的补充校验。"

## 局限性说明（主动坦白，面试追问时用）

- 测试集规模40题、语料39个chunk，仍然是小规模自建数据，问题来源全部人工编写没有引入LLM辅助生成候选，可能存在出题人主观偏向（比如more偏向"能在文档里精确定位答案"的问题，测试集本身对graph2这种精筛策略可能存在一定有利倾向）
- 生成层LLM-as-a-Judge本身也是LLM判断，存在文章提到的"长上下文时偶尔判断出错"的固有局限，本次未做人工抽检校准自动评估结果的准确性（文章方法论里这一步是必要环节，本次因资源和时间限制未覆盡）
- 检索层Recall@k在40题上100%持平，某种程度上是因为测试语料规模小（39个chunk），检索候选池竞争不激烈；如果语料规模扩大到`test/retrieval_two_stage_filtering.md`讨论过的更大规模，Recall层面的差异可能会显现，这是尚未验证的推测
