# 当前无法通过的评测 Case 为什么仍要保留

面试考点：企业 RAG 为什么会把当前版本无法通过的 Case 保留在评测集中，以及如何避免把产品边界、正确拒答和真正的系统缺陷混为一谈。

## 一、先区分两类 Case

### 1. 无法直接回答，但评测通过

例如用户问：

> 客户从北京直营迁到河北代理后，本月商机归谁？

如果系统缺少“河北区域过渡期规则”，合理的期望行为可以是：

- 识别证据不足；
- 不编造客户归属结论；
- 说明缺少哪项规则；
- 引导用户补充条件或查看权威来源。

只要系统完成了这些行为，这条 Case 就应当判定为通过。

因此：

> 无法给出业务结论，不等于评测失败；没有按照预期方式回答、澄清或拒答，才是失败。

### 2. 当前确实无法通过

例如 CRM 操作手册的关键步骤只存在于截图中：

- 评测期望：给出完整、正确且有证据支持的操作步骤；
- 当前系统：只摄取正文文本，无法理解截图里的按钮和箭头；
- 当前结果：答案不完整，因此能力评测失败；
- 临时控制：只展示原始手册链接，不猜测操作步骤；
- 长期方案：建设多模态解析、图文对齐和截图版本治理。

这个 Case 的安全性评测可以通过，但答案完整性评测仍然失败。企业评测通常是多维度的，不能只给一个笼统的“成功”或“失败”。

## 二、为什么保留当前无法通过的 Case

### 1. 量化真实能力边界

不删除失败 Case，团队才能准确知道系统还解决不了多少问题，以及问题集中在哪些类型。

如果为了让报表达到 100% 而删除失败题，得到的只是失真的指标。

### 2. 防止缺陷继续扩大

例如当前有 21 条已知失败。新版本即使暂时没有解决它们，也不能在没有解释的情况下增加到 40 条。

评测集可以检查：

- 已知失败是否仍被安全兜底；
- 原本通过的 Case 是否发生回归；
- 新版本是否引入新的失败类型。

### 3. 验证未来技术改造是否有效

引入多模态解析后，必须重新运行“截图操作流程”Case。只有该 Case 从失败变为通过，才能证明改造真正解决了问题，而不只是完成了代码开发。

### 4. 支撑研发优先级决策

失败 Case 可以与线上数据关联：

- 出现频率；
- 涉及租户和业务线；
- 是否影响开户、客户归属、投放诊断等核心任务；
- 风险等级；
- 修复成本。

产品和研发据此判断应该优先建设多模态解析、时间版本检索，还是跨系统多跳能力。

### 5. 防止技术债被遗忘

每条已知失败都应关联缺陷编号、负责人、临时控制和计划版本。评测集负责持续证明问题是否仍然存在。

如果只把问题写在会议纪要里，几个月后很容易被遗忘。

## 三、评测集必须分层

### 发布门禁集

用于决定版本能否上线，关键 Case 必须全部通过，例如：

- ACL 和租户隔离；
- 高风险业务错误回答；
- 未经确认执行客户归属修改；
- 重复执行开户、审批等有副作用操作。

这些失败不能被平均分抵消。

### 能力基准集

用于观察整体能力变化，可以保留有明确原因的已知失败。

判断标准不是必须达到 100%，而是：

- 核心指标达到发布阈值；
- 新版本不能出现无法解释的回退；
- 新增失败必须完成归因；
- 已知失败有治理记录。

### 挑战集或技术债集

收录当前成本较高的问题，例如：

- 图片和扫描件理解；
- 复杂合并表格；
- 跨文档、跨系统多跳；
- 区域与时间版本冲突；
- 需要实时 CRM 状态才能回答的问题。

这类 Case 用于推动下一阶段能力建设，不直接阻断每次常规发布。

## 四、工程上不能让 CI 永久红灯

已知失败不能直接放进阻断式流水线，然后长期忽略红灯。合理做法是：

- 发布门禁集失败：立即阻断发布；
- 能力基准集失败：计算通过率并与基线版本比较；
- 已知技术债：标记 `known_failure`，绑定缺陷编号和到期时间；
- 已知失败数量增加或原有通过 Case 失败：阻断或人工审批；
- 技术债修复后：移除 `known_failure` 标记，转入固定回归集。

`known_failure` 不是永久豁免。没有负责人、原因和期限的已知失败，本质上就是无人治理的缺陷。

## 五、CRM 业务示例

Case：用户询问“华东 KA 客户转代理后，已承诺返点如何结算”。

正确结论需要组合：

1. 客户归属迁移规则；
2. 全国返点政策；
3. 华东区域过渡期通知；
4. 查询时间对应的有效版本。

当前系统只召回前两项，区域通知排在第 13 名。

可以分别得到以下评测结果：

| 评测维度 | 结果 | 原因 |
|---|---|---|
| Recall@10 | 失败 | 必要的区域通知未进入前 10 |
| 答案完整性 | 失败 | 无法形成完整结算口径 |
| 忠实度 | 通过 | 没有编造缺失政策 |
| 风险控制 | 通过 | 证据不足时停止生成金额结论 |
| 用户引导 | 通过 | 明确提示缺少区域过渡期依据 |

这说明同一条 Case 可以同时暴露能力缺陷，并证明安全兜底有效。

它仍然应该保留，因为未来建设时间感知多跳检索后，`Recall@10` 和答案完整性也应转为通过。

## 六、面试回答模板

> 当前无法通过的 Case 仍然保留，是为了把已知能力缺口变成可度量、可回归的技术债，而不是为了让团队接受一个模糊的失败率。我们会先区分“正确拒答”和“真正失败”：如果问题本来就缺少条件，系统正确澄清或拒答应算通过；只有期望行为明确、但当前能力尚未达到的 Case 才记为失败。这些 Case 会进入能力基准集或技术债集，绑定原因、负责人、临时控制和修复期限。ACL、越权和高风险错答属于发布门禁，必须全部通过。这样既不会为了 100% 删除难题，也不会让已知失败长期留在阻断式 CI 中无人处理。

## 七、核心总结

> 保留失败 Case，不是为了提醒团队“系统做不到”，而是为了持续回答三个问题：缺陷还在不在、新版本有没有变得更差、未来的改造是否真的把它解决了。

如果一个问题在业务上本来就不应该直接回答，应将正确澄清或拒答定义为通过，而不是把它长期保留成失败案例。

## 当前项目事实边界

本文描述的是企业 RAG 的评测治理方法。项目中的指标和业务 Case 用于教学与面试表达，不代表已有真实生产故障台账。面试时应区分已实现能力、原型设计和后续规划。
