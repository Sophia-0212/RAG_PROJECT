# 幂等设计与 request_id 的归属问题

面试考点：`request_id`（幂等键）应该由谁生成——客户端还是服务端？为什么？配合一次真实的线上问题排查故事，能体现排查问题的层次感和跨系统视野，是容易被面试官深挖、也容易拉开候选人差距的一个点。

## 简答版

幂等的核心是——同一个操作，不管重试几次，效果都跟只执行一次一样。实现的关键前提是**幂等键必须由调用方（客户端）生成，不能由服务端生成**。

原因：如果服务端生成 ID，服务端每次收到请求都认为是全新的一次调用，它没有能力判断"这次和上次是不是同一个意图"；只有客户端自己生成 ID、自己记住，才能在网络异常、不确定上次请求有没有成功的情况下，用同一个 ID 重试，让服务端识别出"这是重复提交，别再跑一次了"。

### 因果链条（面试官追问"为什么"时展开）

```
客户端准备发请求前，自己生成一个 request_id（比如 UUID）
        ↓
第一次发送: POST /v1/query, header 带 X-Request-ID: abc-123
        ↓ 假设网络中断，没收到响应（但服务端可能已经收到并在处理）
客户端不知道成功没有，决定重试
        ↓
第二次发送: 同样的 X-Request-ID: abc-123（客户端自己记得住，因为是自己生成的）
        ↓
服务端一看，这个 request_id 之前见过 → 判定为重复提交
        ↓
服务端直接返回第一次那个请求最终跑出来的结果（如果已经跑完），不重新执行
```

如果 ID 只能由服务端生成：客户端在"没收到响应"的情况下，永远无法知道该用哪个 ID 去做幂等重试，因为它压根不知道服务端生成了什么。幂等机制在这种设计下天然失效。

### 实际实现参考（本项目 rag_service/api.py）

```python
supplied = request.headers.get("X-Request-ID")
if supplied and not _REQUEST_ID_PATTERN.fullmatch(supplied):
    ...  # 格式不对，报错
request.state.request_id = supplied or str(uuid4())
request.state.request_id_supplied = bool(supplied)
```

设计是"客户端提供优先，服务端生成兜底"：客户端带了就用客户端的（支持幂等重试），没带就服务端兜底生成一个（不需要幂等保证的简单场景）。

## 深答版——一次线上问题排查故事（面试官追问"踩过什么坑"时用）

按"现象 → 假设 →验证 → 根因 → 修复 → 复盘"的结构讲，不要只讲"我知道幂等很重要"这种空话。

**现象**：RAG 服务上线后，监控发现一个叫 `duplicate` 的指标（衡量同一个 `request_id` 被重复提交的次数）突然从每天几十次，涨到每天几千次，且集中在某几个小时。

**第一轮假设，被推翻**：最初怀疑前端按钮防抖没做好，重复点击导致的。查了当天前端发布记录，那几个小时没有任何前端上线，排除。

**第二轮假设，交叉验证**：查请求耗时直方图（P95/P99 延迟），发现同一时间窗口 P95 延迟从正常的 3 秒涨到 12 秒——正好超过客户端 SDK 默认的 10 秒超时阈值。结合 `duplicate` 指标同时暴增，判断是**客户端超时重试**导致的，不是 bug，是系统真实变慢时幂等机制在正常发挥作用（防止了重复计算，只是重试次数本身暴露了下游变慢这个事实）。

**继续下钻，找到真正根因**：再往下查，那几个小时下游 LLM 推理服务供应商那边有一次容量抖动，导致 LLM 调用延迟涨了 3 倍——这才是根因，`duplicate` 指标只是这个根因在系统上留下的一个"副作用信号"。

**关键判断（体现层次感）**：如果不理解幂等设计原理，看到 `duplicate` 暴增，可能会直接去改前端防抖逻辑，或怀疑幂等键设计错了——这其实是"治标"。真正该做的是顺着这个信号去追下游依赖的健康状态，`duplicate` 在这里应该被当作一个**间接诊断信号**，而不是问题本身。

**修复**：
- 短期止血：给 LLM 调用单独加了一层更激进的熔断+超时收紧，避免慢请求占着并发资源
- 长期治本：把幂等键的存储从单机存储换成跨实例共享的存储——因为当时是单实例部署，如果未来扩容成多实例，同一个 `request_id` 打到不同实例上，幂等判断会直接失效，这是提前发现并修的一处架构债

## 30 秒精简版（面试时间紧张时用）

> "有一次线上 `duplicate` 指标暴增，一开始以为是前端重复提交的 bug，但排查后发现是下游 LLM 服务延迟涨了导致客户端超时重试——`duplicate` 只是幂等机制在正常工作的信号，真正的根因是下游依赖抖动。这次经历让我意识到，监控指标不能只看数值本身，得结合它背后代表的业务语义去判断，同一个指标在不同架构前提下（单实例 vs 多实例）的可信度也不一样。"

这个版本自带"以为是 A，结果是 B"的转折钩子，容易引导面试官主动追问细节，把话题带到你准备好的深度方向。

## 面试官在这类问题里通常评估什么

1. **是否理解"信号"和"根因"的区别**——很多候选人会把异常指标本身当成"要解决的问题"，而不是"通往根因的线索"
2. **是否有跨系统的排查视野**——能否联想到客户端超时阈值、下游供应商容量这些跨越系统边界的因素
3. **是否能分层次给方案**——止血方案和治本方案要分开说，不要只有一种
4. **是否会主动暴露架构债**——最后那句"单实例存储，未来扩容会失效"，是在没被问到的情况下主动展示对系统边界和未来风险的前瞻性认知，比被动回答加分更多
