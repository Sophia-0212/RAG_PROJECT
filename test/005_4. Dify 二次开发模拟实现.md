## 4. Dify 二次开发模拟实现

### 4.1 版本与改动边界

- 2024Q4 从 Dify 0.15 系列建立内部 fork。
- 当时内部版本不能满足企业任务中心、组织数据范围、长时审批和动作审计要求。
- 2025 年完成一次大版本升级，核心 patch 从 41 个缩减到 17 个，其余迁到 Auth Adapter、Approval Service 和 Tool Gateway。
- 每个 patch 记录上游基线、修改原因、影响目录、回归用例和移除条件。

即使当前上游已有 human-input 节点，模拟项目的差异仍是企业身份、任务中心、审批策略、动作 hash、恢复幂等和审计，而不是声称上游永远没有 HITL。

### 4.2 权限模型

使用 RBAC + Data Scope + Policy Obligation：

```
subject:
  tenant_id, user_id, roles, org_path, delegated_by
resource:
  workspace, app, workflow, knowledge_base, tool, customer
action:
  view, edit, publish, run, query, execute, approve
context:
  channel, purpose, risk_level, current_time
decision:
  allow/deny + allowed_scopes + masked_fields + require_approval
```

控制点：

1. Gateway 验证 SSO token 并签发 15 分钟内部身份令牌。
2. Dify API 校验 workspace、app、workflow 的控制面权限。
3. RAG Gateway 将 allowed_scopes 编译为 Milvus metadata filter。
4. Tool Gateway 在动作执行前校验用户权限、资源状态和风险策略。
5. ONECRM 领域服务再次执行领域授权和业务校验。

权限缓存 TTL 为 60 秒，cache key 包含 tenant、user、resource type、action、scope hash 和 policy version。高风险执行和审批恢复不使用旧 allow 缓存。

### 4.3 鉴权改造成果

- 统一收敛 27 个散落的角色判断到 Policy Adapter。
- 建立 86 条资源/动作策略和 42 个跨租户、越权、缓存失效回归用例。
- 权限服务 P95 为 12ms，缓存命中率 93.4%。
- 权限服务不可用时，读公开知识可按缓存策略降级，高敏检索与写动作 fail closed。

### 4.4 Dify 与多副本 RAG 的调用约定

- Dify 传递稳定的 conversation_id、request_id 和可信身份上下文，不依赖命中固定 RAG Pod。
- 任意 Pod 可读取同一运行状态；原执行者丢失后由独立 worker 恢复。运行中返回 HTTP 202 与 `Location`，更晚的新会话轮次返回 409 `CONVERSATION_RECOVERY_PENDING`。
- Redis 协调不可用返回 HTTP 503 `COORDINATION_UNAVAILABLE`，调用方按 `Retry-After` 有界退避，不能无上限重试。
- Dify 不读取 RAG 内部 checkpoint 表，也不承担 RAG 状态迁移职责。
- Dify 对同一逻辑请求必须复用 `X-Request-ID`；不得在超时重试时生成新 ID，也不得用同一 ID 改写 question/constraints。
