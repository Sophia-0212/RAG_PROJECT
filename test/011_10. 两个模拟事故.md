## 10. 两个模拟事故

### 10.1 事故一：审批重复恢复

**现象**：一次部署期间，resume worker 在 CRM 接口已处理但响应丢失后 lease 超时；另一 worker 接管并再次调用。目标接口当时只在工作流层去重，没有领域级 execution_id，导致 6 条客户通知重复发送。

**影响**：

- 42 个审批任务进入结果未知状态。
- 6 个客户收到重复通知。
- 事故持续 31 分钟，18 分钟时关闭受影响通知 Tool。
- 无客户数据覆盖，但产生体验与合规风险。

**根因**：

- 直接原因：worker lease 与下游调用结果之间没有原子边界。
- 系统原因：错误地把工作流消费去重当成业务副作用幂等。
- 监控缺口：只监控任务状态，没有按 execution_id 检查动作重复率。

**处理**：

1. 关闭该 Tool 的恢复入口并保全审计。
2. 按 run_id + node_id + attempt 找出 42 个任务。
3. 通过通知平台查询实际结果，确认 6 条重复。
4. 客服联系受影响客户，未直接删除审计或伪造状态。
5. ONECRM Tool API 增加 execution_id 唯一约束和结果表。
6. Resume 使用 CAS，事件消费增加 inbox。
7. 加入“处理成功但响应丢失”“lease 过期后接管”故障注入。

**结果**：连续五个月未出现同路径重复副作用；幂等命中由新指标单独监控。

### 10.2 事故二：旧版政策文档被引用

**现象**：文档源已撤销一版客户归属政策，但 tombstone 消息在知识摄取死信队列积压，旧 chunk 仍处于 active，导致 11 个回答引用过期政策。

**影响**：

- 97 个请求可能召回旧文档，实际 11 个答案引用。
- 3 名用户按旧流程发起操作，领域服务因规则校验拒绝，未产生错误数据。
- 发现到止血 22 分钟，完整修复 4 小时。

**根因**：

- 删除事件与普通更新共用低优先级队列。
- 监控只有总同步延迟，没有删除/ACL 传播的独立 SLO。
- Context builder 对更新时间排序，但未按 effective_to 强制过滤。

**处理**：

1. 下线旧 index alias 并临时禁用相关问题自动回答。
2. 通过 citation ID 扫描历史 trace 确认影响。
3. 删除/ACL 事件切入高优先级队列，失败立即告警。
4. 检索 filter 强制 status=active 且命中有效时间。
5. 建立 tombstone canary 与 source-index 抽样对账。
6. 将 11 个问题加入版本冲突回归集。

**结果**：删除与 ACL 传播 P99 从 19 分钟降到 3 分 40 秒。
