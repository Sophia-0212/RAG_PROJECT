## 12. 模拟口述答案

### 12.1 30 秒

我有五年后端与智能应用经验，最近三年多聚焦 LLM、RAG 和 Agent。当前项目是在 CRM 场景把知识问答和业务动作做成可生产的 Agent 平台。我负责 Dify 权限适配与 HITL 审批节点，并核心参与 LangGraph + Milvus 的 RAG 引擎。最大的价值不是接入模型，而是把权限、审批、幂等、评测和降级补齐，让 Agent 能在企业数据和动作边界内运行。

### 12.2 三分钟

项目服务 CRM 运营和销售支持。旧流程查一次政策或 SOP 平均需要 6.8 分钟，跨系统动作还缺少统一审计。我们把系统拆成三层：ONECRM 保持客户数据和领域规则；Dify 负责应用和通用工作流；复杂问答由独立 LangGraph RAG 服务负责，Milvus 提供 dense+sparse 混合召回。

我负责两个重点。第一是 Dify 企业化。权限不是接一个 JWT，而是把 workspace、应用、知识库、工具和客户数据范围贯穿到运行时；高风险动作由模型先提出结构化 proposal，Approval Service 固化 action hash 和 checkpoint，审批后重新鉴权，再用 execution_id 调 CRM。这样人工等待不占线程，重复回调和未知结果也不会重复产生业务效果。

第二是 RAG 质量闭环。我们不是复现论文的 reflection-token 模型，而是在 LangGraph 中拆出检索必要性、文档相关性、证据充分性和答案 groundedness 四类判定。普通问题单轮完成，只有 22.7% 的低证据问题进入有界纠错。检索用 BGE-M3 的 dense+sparse、weighted RRF 和 cross-encoder rerank，在锁定测试集上 Recall@10 从 71.3% 到 85.1%，端到端正确率从 66.4% 到 80.1%。与无条件两轮相比，按需策略把 P95 从 4.85 秒降到 3.08 秒。

这个项目让我最深的体会是，生产 Agent 的难点不是 Prompt，而是委托授权、长时状态、业务幂等和可归因评测。现在重做，我会更早把审批状态从 Dify 内核抽离，并在第一版之前先建立失败分桶和 golden set。

### 12.3 被追问“为什么不用 SQLite”时

SQLite 适合本地开发，但我们生产基线有 3 个 Pod，Pod 本地文件既不能共享 checkpoint，也无法用进程锁阻止跨 Pod 的同会话并发。所以我把 durable state 放到 PostgreSQL，把短时协调放到 Redis：数据库负责可恢复与审计，Redis 负责 lease 和全局配额。Redis 故障时 fail closed，不回退本地锁；SQLite 迁移用短维护窗口和幂等工具完成。仓库能证明工程实现和真实依赖集成测试，生产 HA 与 SLO 仍要靠目标集群验证。

### 12.4 被追问“checkpoint 为什么还不等于自动恢复”时

checkpoint 只回答图执行到了哪里，不会主动发现哪个 HTTP 请求死掉了。我又增加了 PostgreSQL request run ledger 和独立 worker：账本用 lease/fencing 决定恢复所有权，worker 恢复前重新鉴权，再看 snapshot 决定重放输入、用 `invoke(None)` 续 pending，还是直接 finalize。结果和对话 turn 单事务去重。这个方案是 at-least-once 节点执行，不会夸成 arbitrary Tool exactly-once。
