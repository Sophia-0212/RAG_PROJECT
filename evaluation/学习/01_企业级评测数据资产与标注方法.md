# 企业级评测数据资产与标注方法

## 1. 学习目标

本文用于回答以下问题：

1. 什么样的评测体系才能证明 RAG 模型质量？
2. 企业级评测数据资产需要建设哪些内容？
3. 百度广告业务方向的 CRM RAG 应覆盖哪些场景？
4. 每条评测数据应该标注什么？
5. 有哪些标注方式，各自适用于什么场景？
6. 如何把评测集接入自动回归和发布门禁？
7. 当前项目距离完整闭环还有哪些差距？

本文中的业务名称、人员、规模和指标均为模拟内容，不代表百度内部真实数据或生产结果。

## 2. 核心结论

要形成“可证明模型质量”的企业级评测体系，需要同时建设三部分：

1. 可审计的评测数据资产。
2. 可重复执行的 Evaluation Runner。
3. 能阻止质量回退版本上线的自动回归门禁。

评测集不是简单收集一批问题，而是一套带有标准判定依据、业务分类、知识版本和标注过程记录的 CRM 业务考试卷。

一个只有问题、没有标准来源和判断规则的文件，不能称为企业级评测集。一个只有评测集、没有自动执行器和发布门禁的项目，也不能称为形成了评测闭环。

## 3. 企业级评测资产包含什么

一个正式评测版本不应只有一个 JSONL 文件，至少需要以下资产：

| 资产 | 作用 |
| --- | --- |
| `cases.jsonl` | 保存问题、身份、标准事实、标准来源和拒答要求 |
| `corpus_manifest.json` | 保存评测对应的知识库快照、文档和版本清单 |
| `annotation_guideline.md` | 定义标注规则、边界情况和正反例 |
| `splits.json` | 定义开发集、锁定测试集和安全挑战集 |
| `dataset_card.md` | 说明数据来源、分布、适用范围和已知偏差 |
| `baseline_report.json` | 保存当前基线系统的评测结果 |
| `change_log.md` | 记录每次增加、修改和删除用例的原因 |
| `adjudication_log.jsonl` | 记录标注分歧、仲裁结论和依据 |

每次评测还必须固定以下版本：

- `dataset_version`：评测数据版本。
- `knowledge_snapshot`：知识库内容快照。
- `index_version`：Milvus 索引版本。
- `embedding_version`：Embedding 模型版本。
- `reranker_version`：重排模型版本。
- `prompt_version`：Prompt 版本。
- `graph_version`：LangGraph 工作流版本。
- `model_version`：生成模型版本。
- `evaluator_version`：评判器或评分规则版本。

缺少这些版本信息时，两次评测结果无法可靠比较。例如 Recall 下降可能来自检索代码，也可能来自知识文档更新或 Embedding 模型变化。

## 4. 广告 CRM 应覆盖的业务场景

项目模拟叙事规划采用 2,400 条 Golden Set；仓库当前已落地的教学 V1 是 64 条，并沿用以下八个一级分桶：

| 分桶 | 模拟数量 | 广告 CRM 示例 |
| --- | ---: | --- |
| 单轮事实 | 620 | 新线索首次跟进时限、客户等级定义、开户材料 |
| 多轮指代与省略 | 360 | “企业客户呢”“刚才那个审批多久完成” |
| 字段名、错误码和缩写 | 310 | 广告主 ID、OCPC、ERP 同步错误码 |
| 多跳组合 | 260 | 客户等级、消耗门槛、折扣资格和审批流程组合判断 |
| 版本与时间冲突 | 210 | 新旧返点政策、生效日期和历史规则 |
| 无答案与歧义 | 260 | 缺少行业、区域或账户类型，需要澄清或拒答 |
| 权限负例 | 240 | 跨区域客户、代理商数据和联系方式导出 |
| Prompt injection 与恶意输入 | 140 | 要求忽略权限、导出隐私或泄漏系统提示词 |

还需要从业务维度保证覆盖：

- 线索管理：线索接入、去重、分配、回收、跟进 SLA、无效线索。
- 客户管理：客户归属、等级、行业、区域、集团关系和生命周期。
- 销售管理：商机阶段、预测、报价、折扣、合同、回款、续费和流失。
- 广告运营：开户、资质审核、充值、退款、预算、素材审核和投放异常。
- 流程审批：跨区归属、价格审批、合同审批和例外处理。
- 系统故障：CRM、广告平台、ERP、工单和消息系统同步问题。
- 安全合规：租户隔离、角色权限、敏感信息、批量导出和审计。

评测集既要接近真实员工问题分布，也要主动提高低频高风险问题的占比。不能因为权限泄漏在线上出现得少，就只放一两条权限用例。

## 5. 每条评测数据应该标注什么

### 5.1 输入和上下文

| 字段 | 含义 |
| --- | --- |
| `case_id` | 全局唯一用例 ID |
| `dataset_version` | 所属数据集版本 |
| `question` | 当前轮用户问题 |
| `conversation_history` | 多轮会话历史 |
| `standalone_query` | 结合上下文后的标准独立问题 |
| `tenant_id` | 模拟租户边界 |
| `user_role` | 销售、运营、主管、质检等角色 |
| `principal_ids` | 权限主体集合 |
| `as_of_time` | 提问发生的业务时间 |
| `knowledge_snapshot` | 应使用的知识快照 |

### 5.2 检索真值

不能只标注“正确文档 ID”，还应标注文档或 chunk 的相关性等级：

| 等级 | 含义 |
| ---: | --- |
| 3 | 直接回答问题的核心证据 |
| 2 | 有帮助但需要结合其他证据 |
| 1 | 与主题相关，但不能支持最终结论 |
| 0 | 不相关或具有误导性 |

推荐记录：

- `relevant_sources`：应召回的文档、版本、chunk 和相关性等级。
- `forbidden_sources`：因 ACL、失效、租户或版本原因禁止召回的来源。
- `expected_route`：预期进入 vectorstore、direct answer、web search 或 refuse。
- `expected_top_k`：计算指标时采用的 TopK 口径。

### 5.3 答案真值

生成答案不适合用字符串完全相等判断，应拆成原子事实：

- `required_facts`：答案必须包含的事实。
- `optional_facts`：允许补充但不强制要求的事实。
- `forbidden_facts`：旧政策、错误金额、错误步骤等禁止出现的内容。
- `fact_evidence_map`：每个事实对应的证据文档、版本和 chunk。
- `reference_answer`：用于帮助理解的参考答案，不作为唯一正确措辞。
- `expected_action`：应给出的审批、转人工、查询日志或下一步操作。

例如“客户认为广告价格太高时应该怎么处理”，参考答案可以有不同措辞，但必须覆盖：认可客户顾虑、确认对比对象、说明差异化价值、让价必须走价格审批并留痕。

### 5.4 拒答、安全和风险

- `answerability`：answerable、unanswerable 或 ambiguous。
- `should_refuse`：是否必须拒答。
- `expected_refusal_reason`：标准拒答原因码。
- `required_clarifications`：歧义问题必须追问的信息。
- `risk_level`：normal、important 或 critical。
- `security_policy`：该用例验证的租户、ACL、隐私或注入规则。

## 6. 标注对象和标注形式

“标注什么”和“怎样组织标注结果”是两个不同问题。

| 标注形式 | 示例 | 适合评价什么 |
| --- | --- | --- |
| 二分类 | 应拒答/不应拒答 | 拒答、安全和路由 |
| 多分类 | vectorstore/web/refuse | 问题路由 |
| 有序等级 | chunk 相关性 0～3 | 检索、重排 |
| 集合标注 | 多个 relevant chunk | Recall、Citation Recall |
| Span 标注 | 文档中的证据句范围 | Claim Groundedness |
| 原子事实清单 | 必须事实、禁止事实 | 答案正确性和完整性 |
| Pairwise 偏好 | 答案 A 优于答案 B | 帮助性、清晰度和可执行性 |
| 量表评分 | 正确性 1～5 | 难以完全结构化的语义质量 |
| 程序断言 | 召回结果不得包含跨租户文档 | ACL、安全和时间有效性 |

对于高风险 CRM 问题，应优先使用可确定判分的事实、来源、权限和版本标签，不能只使用主观的 1～5 分。

## 7. 有哪些标注方式

### 7.1 业务专家人工标注

由熟悉线索、销售、广告运营和审批制度的业务专家直接标注。

适合政策、审批、折扣、权限、客户归属等高风险事实。优点是真值可信，缺点是成本高、速度慢。

### 7.2 双人独立标注加第三人仲裁

两名标注员独立处理同一条数据，互相看不到对方结论。有分歧时由更资深的业务专家仲裁。

这是企业 Golden Set 和安全集的推荐方法。它不仅产生最终标签，还能发现标注规范本身是否含糊。

### 7.3 单人标注加抽样复核

一人完成标注，另一人随机抽查一定比例。

适合低风险、规则清晰和数据量较大的普通事实问题，不适合权限、金额、政策和审批问题。

### 7.4 规则或程序化标注

利用数据库字段、文档元数据和业务规则自动生成标签。

适合错误码映射、文档有效期、路由、ACL 和已知字段定义。例如用户没有 `group:finance` 时，财务受限文档可以自动加入 `forbidden_sources`。

风险是规则写错后会批量污染数据，因此程序标签也必须抽样审核。

### 7.5 LLM 辅助标注

LLM 可以帮助：

- 从权威文档中提取候选原子事实。
- 根据文档生成不同表达的问题。
- 对问题做业务分类和风险预分类。
- 找出答案中可能缺失或矛盾的事实。

LLM 只能作为预标工具。对于高风险真值，不能让 LLM 生成标签后未经人工审核直接进入锁定测试集，也不能使用被测模型给自己生成标准答案。

### 7.6 合成数据生成

根据权威文档和业务模板生成新问题，适合全新业务、边界条件、多轮省略和恶意输入。

合成问题必须绑定真实模拟文档，并经人工检查语言是否符合员工真实表达。否则很容易形成“模型生成问题、模型又特别擅长回答”的虚高数据集。

### 7.7 线上日志回流

从真实搜索、用户反馈、转人工记录和失败 Trace 中采样问题。

优点是贴近真实分布；缺点是包含隐私、重复问题和历史系统偏差。必须先脱敏、去重、聚类，再由专家重新标注，不能直接把点赞或点踩当作正确性真值。

### 7.8 Pairwise 两两比较

让标注员比较候选答案 A 和 B 哪个更好，常用于 Prompt、模型和回答风格实验。

Pairwise 适合判断帮助性、清晰度和操作完整度，但“A 比 B 好”不代表 A 的事实一定正确，因此不能替代 Groundedness 和事实标注。

### 7.9 红队标注

由安全、业务和算法人员主动构造越权、Prompt injection、隐私导出、角色伪造和跨租户访问问题。

红队集应独立维护，部分用例对开发人员隐藏，避免系统只针对公开攻击模板做硬编码。

## 8. 推荐的组合标注策略

企业项目不应只选择一种标注方式，推荐组合如下：

1. 线上日志和业务需求提供真实问题分布。
2. 权威业务文档提供事实和版本依据。
3. LLM 生成候选问题并完成预标。
4. 普通低风险数据采用单人标注加抽检。
5. 高风险、权限和锁定测试数据采用双人独立标注。
6. 分歧数据由高级 CRM 业务专家仲裁。
7. 安全团队构造独立红队挑战集。
8. 线上失败案例经审核后进入下一版评测集。

## 9. 如何保证标注可信

### 9.1 先制定规范，再大规模标注

标注规范需要明确：

- 什么叫相关文档，什么叫核心证据。
- 正确但无法帮助用户完成任务是否算有帮助。
- 信息不足时应该追问还是拒答。
- 新旧政策冲突时如何选择版本。
- 什么情况下必须转人工或触发审批。
- 不同角色能够看到哪些字段和文档。

每条规则都需要正例、反例和边界例。

### 9.2 先做 Pilot

正式标注前先选择 100～200 条代表性数据做试标，统计分歧并修订规范。不要一开始就让多人直接标 2,400 条，否则规范问题会批量扩散。

### 9.3 标注一致性

可以使用：

- 二分类或多分类：Cohen's Kappa。
- 0～3 等级相关性：Weighted Kappa。
- 多人、多类别标注：Krippendorff's Alpha。
- 文档或事实集合：Precision、Recall、F1 或 Jaccard。

`0.85` 可以作为高风险标签的初始一致性目标，但不能机械用于所有任务。若一致性低，优先修正规范，不应通过简单投票掩盖分歧。

### 9.4 防止数据泄漏

评测数据必须按来源文档、问题模板和业务事件分组切分。

不能把“新线索多久联系”放入开发集，再把“首次跟进时限是多少”放入锁定测试集。两条只是同义改写，会造成测试指标虚高。

建议使用：

- 600 条开发集：允许算法工程师查看，用于调参和错误分析。
- 1,800 条锁定测试集：由评测负责人管理，用于正式回归。
- 在锁定测试集中保留独立安全挑战子集和高风险业务子集。

## 10. 应计算哪些指标

### 10.1 检索和排序

- Recall@K：应该召回的证据是否进入 TopK。
- Hit Rate@K：TopK 中是否至少命中一条正确证据。
- MRR：第一条正确证据排得是否足够靠前。
- nDCG@K：结合 0～3 相关性等级评价整体排序质量。

### 10.2 生成和引用

- Fact Coverage：必须事实覆盖率。
- Fact Correctness：回答中的事实是否正确。
- Claim Groundedness：每个答案主张是否都有证据支持。
- Citation Precision：已引用来源中有多少真正支持答案。
- Citation Recall：应引用的关键来源是否引用完整。

### 10.3 拒答和安全

- Refusal Precision：被拒答的问题中有多少确实应该拒答。
- Refusal Recall：应该拒答的问题中有多少成功拒答。
- Clarification Accuracy：歧义问题是否正确追问。
- ACL Leakage Rate：召回或回答是否暴露无权内容，目标必须为 0。
- Effective Version Accuracy：是否使用提问时间对应的有效政策版本。
- Prompt Injection Success Rate：攻击是否成功改变系统安全边界，目标必须为 0。

### 10.4 业务和效率

- Task Completion：答案是否让员工知道下一步怎么操作。
- Escalation Accuracy：是否在正确场景转人工或进入审批。
- P50/P95/P99 延迟。
- 平均 Token、模型调用次数和单位成功回答成本。

业务、安全和效率指标要分别展示，不能用一个“综合分”掩盖权限泄漏或高风险政策错误。

## 11. 自动回归闭环

```text
线上日志 / 业务需求 / 事故案例
              |
              v
      脱敏、去重、聚类和分桶
              |
              v
      标注、复核、仲裁和版本发布
              |
              v
评测数据版本 + 知识快照 + 标注规范
              |
              v
Runner 执行基线版本和候选版本
              |
              v
检索、生成、引用、安全、成本分桶报告
              |
              v
   发布门禁：通过上线 / 失败阻断
              |
              v
Prometheus、用户反馈、人工抽检和 A/B
              |
              +------> 审核后进入下一版评测集
```

推荐执行频率：

- 每个 PR：运行 50～100 条确定性 smoke 和 security 用例。
- 每晚：运行受本次变更影响的业务分桶。
- 每周：运行完整锁定评测集。
- 模型、Prompt、Embedding、Reranker 或索引发布前：运行完整候选版本与生产基线对比。
- 线上事故修复：必须新增对应回归用例。

## 12. 发布门禁如何设计

门禁必须同时考虑绝对阈值、相对回退和高风险硬门禁。

### 12.1 绝对阈值

例如 Recall@5 不得低于 0.80、Citation Precision 不得低于 0.90。

### 12.2 相对回退

即使候选版本仍高于绝对阈值，只要相对生产基线下降超过允许范围，也应该阻止发布。例如生产 Recall@5 是 0.88，候选版本下降到 0.81，虽然仍大于 0.80，但下降幅度已经值得调查。

### 12.3 高风险硬门禁

以下指标不能被普通问题的高分抵消：

- ACL Leakage Rate 必须为 0。
- Prompt injection 攻击成功率必须为 0。
- 高风险政策版本正确率必须为 100%。
- 关键审批和隐私拒答用例必须全部通过。

### 12.4 分桶门禁

除了总体指标，还要分别检查线索、客户、商机、广告运营、审批、故障、安全、多轮和版本冲突等分桶，避免总体平均值掩盖局部严重回退。

## 13. 当前项目已经有什么

当前项目已经有以下评测基础：

- `evaluation/datasets/ad_crm_golden_small_v1.jsonl`：64 条、八类各 8 条的高保真虚构黄金集。
- `evaluation/corpus/ad_crm_v1/`：包含当前、历史、受限和隔离来源的冻结知识快照。
- `evaluation/schema.py`：身份、权限、时点、版本、证据、事实和标注审计校验。
- `evaluation/assets.py`：知识文件、证据引用、有效期、回答侧 ACL、切分和仲裁状态自检。
- `evaluation/metrics.py`：Recall@K、MRR、nDCG、引用、事实覆盖和禁止事实指标。
- `evaluation/runner.py` 与 `evaluation/run_cli.py`：离线预测评分、切片、失败明细和门禁执行。
- `evaluation/DATASET_CARD.md`、`ANNOTATION_GUIDE.md`、`PREDICTION_CONTRACT.md`：数据治理和使用契约。
- `tests/test_evaluation_*.py`：数据资产、Schema、指标和 Runner 的确定性回归测试。

这些能力已经形成“冻结资产 → 离线预测 → 确定性评分 → 发布门禁”的最小闭环，但还不是生产模型质量证据。

## 14. 当前项目还缺什么

1. 编写生产 API 回放适配器，真实生成检索、路由、答案和引用预测文件。
2. 用脱敏线上日志和真实业务专家标注逐步扩展到规划的 2,400 条，而不是批量复制模板。
3. 增加 claim 级 Groundedness、矛盾检测和经校准的 LLM Judge，并保留人工抽检。
4. 实现 candidate 与 baseline 的配对差异、置信区间和显著性判断。
5. 把 development/security、nightly、weekly 和 pre-release 评测接入分层 CI。
6. 建立线上失败样本脱敏、去重、双人复核、仲裁和版本升级流程。

当前代码和门禁已统一使用 Recall@10。模拟叙事中的百分比仍是演练数据，只有 Runner 对真实候选预测生成的报告才是本项目的实测证据。

## 15. 面试表达

可以这样介绍：

> 我们没有把评测集理解成一批静态问答，而是将它建设成版本化的数据资产。每个版本绑定知识快照、标注规范、数据切分和评判器版本。数据来源包括脱敏线上日志、业务需求、事故案例和红队攻击；高风险数据采用双人独立标注和专家仲裁。发布时 Runner 同时执行生产基线和候选版本，分别评估检索、事实覆盖、Groundedness、引用、拒答、版本和 ACL，并设置安全硬门禁。线上失败案例经过审核后进入下一版数据集，从而形成离线评测、发布门禁和线上反馈回流的闭环。

真正能够证明质量的不是“有 2,400 条数据”，而是这批数据覆盖明确的 CRM 风险空间，真值经过可审计标注，评测过程能够复现，坏版本会被门禁阻止，线上失败还会持续进入下一版评测资产。
