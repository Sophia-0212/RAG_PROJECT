# 企业级 RAG 评测集学习路线图

> 适用对象：做过 AI Agent/RAG 项目，但缺少企业级评测、数据治理和发布门禁经验的工程师。
>
> 学习目标：不仅能运行评测脚本，还能从 CRM 业务目标出发创建评测集，解释人工标注与 AI 辅助标注的边界，分析评测报告，并在面试中经得住业务、算法和工程追问。

## 一、先建立完整心智模型

企业级 RAG 评测不是一个 JSONL 文件，而是一条可以审计的数据与工程链路：

```text
业务需求、用户日志、线上事故、知识变更、安全攻击
                         ↓
              定义评测目标和风险空间
                         ↓
        冻结知识快照 corpus + 版本/ACL/有效期
                         ↓
      构造问题并标注动作、证据、事实和禁止项
                         ↓
       双人复核、专家仲裁、去重和防泄漏切分
                         ↓
              发布版本化 Golden Set
                         ↓
       候选 RAG 运行后生成 predictions 答卷
                         ↓
       Runner 逐题评分，Metrics 汇总不同切片
                         ↓
               Gate 决定能否发布
                         ↓
          线上失败脱敏审核后进入下一版本
```

学习时始终追问三个问题：标准答案从哪里来；为什么当前用户有权得到它；系统如何把结论变成可重复计算的指标。

## 二、`evaluation/` 目录应该怎样理解

不要按照文件名字母顺序阅读。按职责把目录分成六层：

| 层次 | 主要文件 | 解决的问题 |
| --- | --- | --- |
| 学习与治理 | `学习/`、`DATASET_CARD.md`、`ANNOTATION_GUIDE.md`、`CHANGELOG.md` | 为什么评、怎么标、版本如何管理 |
| 业务真值 | `corpus/ad_crm_v1/`、`manifest.json` | 正确答案依据哪份知识、哪个版本和权限 |
| 黄金标签 | `datasets/ad_crm_golden_small_v1.jsonl`、`dataset_release.json` | 每道题的标准判定是什么 |
| 数据契约 | `schema.py`、`assets.py`、`PREDICTION_CONTRACT.md` | 数据是否合法、预测答卷长什么样 |
| 质量评测 | `metrics.py`、`runner.py`、`run_cli.py`、`gate.py`、`release_gate.json` | 如何逐题评分、汇总并决定发布 |
| 性能评测 | `performance.py`、`load_test.py`、`state_load_test.py` | 延迟、吞吐、并发和状态后端是否达标 |

`cli.py` 是只对已有指标 JSON 执行门禁的轻量入口；`run_cli.py` 才是从逐题预测到完整报告的主入口。质量评测和性能压测是两套问题，面试时不要把 Recall@10 与 P95 混成一个概念。

## 三、阶段 1：理解“为什么需要评测集”

### 阅读

1. `DATASET_CARD.md`
2. `学习/01_企业级评测数据资产与标注方法.md` 的第 1～4 节

### 必须理解

- 评测集不是问题集合，而是问题、上下文、身份、时间、证据、标准事实和判定规则的组合。
- 离线评测解决“候选版本上线前有没有退化”，线上指标解决“真实用户是否受益”，二者不能相互替代。
- 总体平均分可能掩盖权限、版本和高风险业务分桶的严重问题。
- 64 条 V1 是可执行教学资产，不代表真实员工问题分布；2,400 条是模拟扩数目标。

### 练习

不用看代码，用自己的话解释：为什么只有“问题 + 标准答案”的 Excel 不能证明企业 RAG 质量。

### 练习参考答案

业务真值不是一句"标准答案文字"，是这一整套"这份知识是什么、什么时候生效、谁能看、具体在哪个章节"的结构化信息。评测时,判断一个候选答案对不对,不只是看文字像不像,是看它有没有引用正确的source_id+version_id+section，在正确的acl权限范围内。

Excel 至少漏掉四点：

- **权限**：答案文字对，但若在不该给这个用户看的范围内答出来，是泄漏事故，不是“答对”。
- **时效**：制度会变，不标版本/时间点，模型答旧版本数字也可能文字命中，但对当前用户是错的。
- **证据溯源**：企业要求答案可审计，只比对文字，模型可能靠错误证据拼出相似回复——答案对、证据错，比不出来。
- **切片能力**：一个平均分会被大量简单题掩盖少数高风险题（泄漏、价格错误）的失败。

### 面试验收

能够回答：你们为什么不用用户点赞率直接代替离线 Golden Set？

### 面试验收参考答案

点赞率是线上、有偏、滞后的信号；Golden Set 是离线、可控、可复现、能提前拦截问题的信号，两者不能互相替代，企业里通常并用。

- **事后 vs 事前**：点赞发生在答案已经送达用户之后，出了权限泄漏/价格承诺错误也无法撤回；Golden Set 在上线前拦截，不让问题发布出去。
- **有偏采样**：高风险但低频的场景（权限边界、注入攻击）真实用户很少碰到，点赞数据里样本量不够；Golden Set 可以故意构造这类高风险用例。
- **点赞≠证据严谨**：用户点赞反映“看起来靠谱”，不代表引用的证据、版本、事实覆盖是对的，普通用户没能力核实证据链。
- **无法做对照实验**：Golden Set 能让生产基线和候选版本跑同一批题逐题对比；点赞率没法让同一用户同时评价两个版本。

## 四、阶段 2：理解业务真值（source_id+version_id+acl+sections）和冻结知识快照（snapshot_id+as_of）

### 阅读

1. `corpus/ad_crm_v1/README.md`
2. `corpus/ad_crm_v1/manifest.json`
3. `lead_governance_v2.md` 与 `lead_governance_v1_retired.md`
4. `restricted_rate_card_q3.md` 与 `untrusted_upload.md`

### 必须理解

- `active` 文档用于当前问答，`retired` 文档用于历史复盘。
- `restricted` 文档可以存在于知识系统中，但不能被无权限用户召回或引用。
- `quarantined` 内容属于不可信数据，里面的文字不能获得系统指令权限。
- `source_id + version_id + section_id` 才能把一个答案事实定位到可复核证据。
- `as_of` 决定哪个版本在提问时点有效，不能简单地认为“最新版永远正确”。

### 练习

分别回答：2026 年 9 月和 2026 年 6 月的线索首次联系时限是什么，为什么两个答案都可能正确。

### 练习参考答案

- **2026 年 9 月** → 引用 `v2.1.0`（active）：工作日 18:00 前分配的高意向线索，4 个工作小时内完成首次有效联系；18:00 后或非工作日分配的，从下一个工作日 09:00 起计时。
- **2026 年 6 月** → 引用 `v1.4.0`（retired）：新分配线索须在 24 小时内首次联系，超过 48 小时提醒，超过 72 小时无跟进自动回收。

两个答案都对，因为判断标准不是“哪个版本更新”，是“`as_of` 落在哪个版本的 `[effective_from, effective_to)` 区间内”——`v2.1.0` 从 2026-07-01 才生效，`v1.4.0` 到 2026-06-30 才失效，两者时间区间不重叠，各自在自己的窗口内都是唯一正确答案。

### 面试验收

能够回答：知识库里同时存在新旧 SOP 时，如何评测模型是否引用了正确版本？

### 面试验收参考答案

不能只比文字，要看两点：答案能否定位到确切的 `source_id + version_id + section`（不是笼统一句话）；这个 `version_id` 是否匹配题目 `as_of` 当时生效的版本（不能拿现在最新版本去答历史时间点的问题）。命中对了 `source_id` 但 `version_id` 选错、或引用了 `as_of` 那一刻还没生效的版本，都判定为版本错误，答案文字通顺不能抵消版本判断错误。

## 五、阶段 3：掌握评测集创建流程

一个接近真实企业的创建流程如下：

1. 明确评测对象：Retriever、Reranker、生成模型、安全策略或端到端系统。
2. 建立业务分类和风险矩阵，确定高频、高损失和监管敏感场景。
3. 收集候选案例：脱敏线上日志、搜索无结果、客服升级、需求卡片、事故复盘和红队攻击。
4. 清洗数据：去除个人信息、客户机密、重复模板、无业务意义问题和无法复现案例。
5. 冻结知识快照，记录来源、版本、有效期、ACL 和内容指纹。
6. 还原提问环境：租户、角色、团队、时间、多轮历史和必要业务状态。
7. 判断预期动作：`answer`、`clarify` 或 `refuse`。
8. 标注相关证据、相关性等级和必须引用的核心证据。
9. 将标准答案拆成最小事实，并标禁止证据、禁止事实和拒答原因。
10. 独立复核和专家仲裁，记录标注规范版本与审计状态。
11. 按来源文档和问题模板分组切分，避免同义问题跨集合泄漏。
12. 运行 Schema、ACL、时间和证据一致性校验，计算指纹后发布数据版本。
13. 用生产基线和候选版本分别运行，分析整体指标、切片和逐题失败。
14. 线上失败只有在脱敏、去重、绑定证据并重新审核后，才能进入下一版。

### 练习

选择一个“客户要求把预算从 10 万提到 14 万”的需求，完整写出身份、时间、预期动作、证据、必须事实和禁止事实。

### 面试验收

能够不看文档，从数据来源一直讲到版本发布和线上失败回流。

## 六、阶段 4：人工标注、AI 自动标注和 AI 辅助标注

### 1. 人工标注是什么

人工标注不是让标注员凭经验写一个流畅答案，而是让对结论负责的人依据冻结证据确认业务真值。

| 角色 | 主要责任 |
| --- | --- |
| CRM 业务专家 | 判断线索、客户、商机和销售流程是否正确 |
| 商务/财务专家 | 判断价格、折扣、返货、合同和结算规则 |
| 运营专家 | 判断开户、创意、预算和异常处置流程 |
| 安全专家 | 判断租户、角色、敏感信息和 Prompt Injection 边界 |
| 评测工程师 | 将业务结论转换为稳定、可计算的数据标签 |

高质量人工流程通常是标注员 A、B 独立判断，普通分歧由业务专家仲裁，权限和高风险政策分歧不能靠简单多数票解决。

### 2. AI 自动标注是什么

AI 自动标注是让模型或规则直接产生标签。例如：LLM 判断回答是否 grounded、规则判断是否命中禁止 source、模型自动拆分答案 claim。

它速度快、成本低、容易扩大规模，但会继承 Prompt 偏差、模型幻觉和位置偏差。AI 给出的标签不因为格式完整就自动成为真值。

### 3. AI 辅助标注是什么

AI 辅助标注更适合企业 Golden Set：AI 先聚类日志、去重、推荐证据、生成候选问题、拆分事实和给出初始标签，人类负责确认和修改。

推荐流程：

```text
规则/AI筛选候选案例
        ↓
AI生成预标注和候选证据
        ↓
人工独立复核业务结论
        ↓
高风险或分歧样本专家仲裁
        ↓
确定性程序检查结构和引用
        ↓
抽样审计AI与人工一致性
```

### 4. 哪些内容不能完全交给 AI

- 当前真实制度和历史制度之间的最终有效性判断。
- 细粒度 ACL、跨租户边界和侧信道泄漏判断。
- 价格承诺、合规准入、账户暂停等高损失结论。
- 知识库没有答案时，模型自己生成的“标准答案”。
- LLM Judge 对自己同系列模型答案给出的未经校准评分。

当前数据中的 `synthetic_sme` 和 `adjudicated` 是高保真模拟字段，不表示真实百度业务专家已经执行了双人标注和仲裁。面试时必须明确这一点。

### 练习

选择 `AC-001`，说明哪些字段可以由程序自动校验，哪些结论必须由安全和商务人员确认。

### 面试验收

能够回答：既然大模型能生成评测数据，为什么还要业务专家？如何控制 LLM-as-Judge 偏差？

## 七、阶段 5：学会逐字段阅读一条评测案例

### 阅读顺序

1. `case_id`、`category`、`business_domain`：这道题属于什么能力和业务。
2. `tenant_id`、`principal_ids`：谁在问，能访问什么。
3. `as_of`：按哪个时间点判断制度。
4. `history`、`question`：用户完整意图是什么。
5. `expected_action`、`expected_route`：应该答、澄清还是拒绝，以及走哪条链路。
6. `relevant_sources`：正确证据的来源、版本、章节和相关性等级。
7. `required_facts`：答案必须覆盖哪些独立事实，允许哪些表达形式。
8. `forbidden_source_refs`、`forbidden_facts`：真正要防止的生产事故是什么。
9. `risk_level`、`split`、`annotation`：如何切片、是否允许开发调参、标签是否完成审核。

### 推荐案例顺序

`SF-001` → `MT-002` → `TM-006` → `MH-002` → `TV-001` → `AN-002` → `AC-001` → `PI-002`。

这条顺序依次引入单事实、多轮上下文、错误码、多文档组合、历史版本、澄清、权限和检索注入。

### 面试验收

随机打开一条 JSONL，能够在三分钟内说明它测什么、怎样才算通过、最危险的错误答案是什么。

## 八、阶段 6：理解 Schema 和资产治理

### 阅读

### 必须理解

- Schema 校验结构正确，不等于业务事实一定正确。

## 九、阶段 7：理解指标，而不是只背公式

### 阅读

1. `metrics.py`
2. `学习/01_企业级评测数据资产与标注方法.md` 的指标章节

### 指标与业务含义

| 指标 | 回答的问题 |
| --- | --- |
| Recall@10 | 必须证据是否进入前 10 个候选 |
| MRR | 第一份有效证据出现得是否足够靠前 |
| nDCG@10 | 高相关证据是否排在低相关证据前面 |
| Citation Precision | 引用的材料有多少真正支持答案 |
| Citation Recall | 必须引用的证据是否引用完整 |
| Fact Coverage | 答案覆盖了多少必须业务事实 |
| Refusal Precision/Recall | 拒答是否过多，以及该拒绝时是否拒绝 |
| ACL Leakage Rate | 检索或引用阶段是否接触禁止证据 |
| 分桶 Pass Rate | 哪类业务或风险正在退化 |

指标必须说明分母、样本范围、K 值和知识快照。不能只说“准确率 90%”而不说明是什么准确率。

### 练习

构造一个 Recall@10 为 1，但 Citation Recall 和 Fact Coverage 不为 1 的答案，解释为什么“检索到了”不等于“回答正确”。

### 面试验收

能够解释 Recall、nDCG、Groundedness、Citation 和端到端正确率分别测哪一层。

## 十、阶段 8：理解 Runner、报告和发布门禁

### 阅读

1. `PREDICTION_CONTRACT.md`
2. `runner.py`
3. `run_cli.py`
4. `gate.py`
5. `release_gate.json`

### 运行链路

```bash
.venv/bin/python -m evaluation.run_cli \
  path/to/candidate_predictions.jsonl \
  --output .rag-state/evaluation/candidate-report.json
```

Runner 要完成四件事：检查预测覆盖是否一条不多一条不少；逐案例比较动作、路由、证据和事实；按业务、类别、风险和 split 汇总；保留每一条失败原因。

Gate 要同时包含普通质量阈值和安全硬门禁。权限泄漏、Prompt Injection 成功和关键版本错误不能被大量简单题的高分抵消。

当前 Runner 消费离线预测文件，不会主动请求生产 API。生产 API 回放适配器是下一层待建设能力；没有真实候选预测文件时，不能声称已经测得模型质量。

### 练习

阅读 `tests/test_evaluation_runner.py`，说明为什么临时“完美预测”只能证明评测器正确，不能证明 RAG 模型正确。

## 十一、阶段 9：区分质量评测与性能评测

### 阅读

1. `performance.py`
2. `load_test.py`
3. `state_load_test.py`

### 必须理解

- 质量评测固定输入，观察回答和证据是否正确。
- 性能评测施加并发与流量，观察 P50/P95/P99、吞吐、错误率和资源瓶颈。
- 状态后端压测关注 PostgreSQL/Redis 的锁、checkpoint、会话和配额容量。
- 一个系统可以回答很准但延迟不可接受，也可以很快但答案不可信，两类门禁都需要。

### 面试验收

能够分别设计一次 Recall 回归实验和一次峰值 QPS 容量实验，不混淆实验变量。

### 推荐回答结构

用“业务风险—数据构建—标注治理—自动评测—发布门禁—线上回流”六段表达：

> 我们先按 CRM 高频场景和高风险场景定义评测空间，数据来源包括脱敏日志、业务需求、事故和红队攻击。每条样本绑定冻结知识快照、用户身份、提问时点、版本化证据、必须事实和禁止项。AI 用于日志聚类、去重、候选证据和预标注，最终业务真值由双人复核与专家仲裁确认。候选系统产生逐题预测后，Runner 分别评估检索、排序、事实覆盖、引用、拒答、版本和 ACL，并按业务与风险切片。普通指标采用阈值和相对回退，权限与注入采用硬门禁；线上失败经脱敏审核后进入下一版评测集。

对于当前项目，要补充说明：上述人工流程是企业目标方法；仓库中的 64 条数据是高保真模拟教学资产，不是百度内部数据，也不是生产模型质量证明。

## 十四、最终验收清单
